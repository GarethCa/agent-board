# Theme tokens

The app's look lives in one file, `apps/desktop/src/renderer/src/tokens.css`, as CSS custom properties on `:root`. It holds the Workbench light theme and, under `:root[data-theme='dark']`, the dark one. Every other stylesheet and component uses `var(--token)`, so a theme is a set of overrides for these properties.

## Rules

- **Only `tokens.css` writes a literal** colour, spacing, radius, font, shadow, filter or motion value. `tokens.test.ts` parses every stylesheet (postcss) and every `.ts` and `.tsx` file (the TypeScript compiler) in the renderer, and reports each offence as `file:line`. It catches:
  - colours anywhere: hex, any colour function (`rgb()`, `hsl()`, `hwb()`, `lab()`, `lch()`, `oklab()`, `oklch()`, `color()`) and every CSS named colour
  - in CSS, a number in `padding`, `margin`, `gap`, `border-radius`, `font*`, `letter-spacing`, `line-height`, `box-shadow`, `text-shadow`, `filter`, `backdrop-filter`, `animation*` or `transition*`, and an easing keyword or function outside a token
  - in TypeScript, the same keys in any object (a `style` object, inline or not, and options such as `duration`), paint keys (`color`, `fill`, `background`, xterm's `foreground`...) and SVG paint attributes (`fill`, `stroke`...) that hold anything but a `var()`, `none`, `currentColor`, `transparent` or `inherit`, and SVG font attributes
  - a `var(--x)` or `token('--x')` that names no token, and a token that nothing reads

  In prose, a hex colour needs six or eight digits, or a letter, to count, so `PR #123` is not one. A value held in a variable (`fontSize: size`) isn't checked.
- **Each role has its own token**, named for the role, not its look: `--primary` for the primary button's fill, not `--text`, even though the light theme fills it with the text colour. If a role should look like another, alias it (`--primary: var(--text)`). A theme then overrides the literals and the aliases follow, unless it overrides them too. A dark theme can then flip `--text` light and keep `--on-primary` readable by overriding `--on-primary` alone.
- **A rule may set its own local property** to pick between tokens, for example `--tile-state` per agent state or `--pr-bg` per PR state. Local properties are listed in `tokens.test.ts`.
- **Code that needs a resolved value** (xterm's canvas, React Flow's dot grid and `fitView` duration) reads it with `token()` or `tokenNumber()` from `theme.ts`. `tokenNumber` returns px for lengths and ms for durations (written in `ms` or `s`), and throws on a token that is missing or isn't one of those. The terminal re-reads its tokens, its 16 ANSI colours included, when `data-theme` changes.
- **Stored colours are drawn by name.** A sticky note's, text item's, shape's or connector's colour is stored data, the light theme's hex from a protocol preset (`STICKY_COLORS`, `TEXT_COLORS`, `SHAPE_FILLS`, `SHAPE_STROKES`), which no theme rewrites. `board-colors.ts` draws each preset through a token named for it instead: `--sticky-<name>` and `--sticky-<name>-ink` for a note's paper and ink, `--paint-<name>` for text, a connector or an outline on the desk, `--shape-fill-<name>` for a fill and `--shape-ink-<name>` for text in a filled shape, which is on paper in every theme. The light theme's values are the stored ones (`tokens.test.ts` checks), and a colour that is no preset is drawn as stored. They are set on the element as `--sticky-color`, `--sticky-ink`, `--item-color`, `--shape-fill`, `--shape-stroke` and `--connector-color`.
- **Out of scope**: layout geometry, meaning widths, heights, positions and border widths that fit one component; the character SVGs' drawing coordinates; and zone colours, which the daemon assigns from `ZONE_COLORS` and are set as `--zone-color` (a theme tints them through the `--zone-*-mix` tokens).

## Themes

A theme is a set of token values and nothing else. The light theme is `:root`; each other theme is one `:root[data-theme='<id>']` block in `tokens.css`. The registry, `apps/desktop/src/shared/themes.ts`, lists each theme as data: its id, its name in Settings, whether it is light or dark, whether System shows it for that mode (one per mode), and its desk colour. v1 has two: Workbench light ("Light") and the dark **Warm graphite** ("Dark", AN1), which sets `color-scheme: dark` so native controls and scrollbars follow.

Which theme shows is the Appearance setting, Settings › Appearance: System (the default) or any theme in the registry. The main process keeps it in `appearance.json` in the app's data folder (written whole, then applied), points Electron's `nativeTheme.themeSource` at the theme's light or dark mode before any window opens, and sends every window each new pick. A window opens with the setting in its query, so its first paint is right; `followTheme()` (`renderer/src/themes.ts`) sets `data-theme` on `<html>` from the setting, or under System from `prefers-color-scheme`, and again whenever the OS or the setting changes it. A new window's background is its theme's desk, so nothing flashes.

To add a theme, add its block in `tokens.css` and its entry in `shared/themes.ts`: it becomes a choice in Settings › Appearance with no other code. `tokens.test.ts` holds every theme in the registry to the rules the dark one meets:

- Its block exists, with its `color-scheme`, and its `--surface` is its registry desk.
- It sets every colour the light theme writes as a literal, the 16 ANSI colours included, bar a short list that is the same in every theme (`SAME_IN_EVERY_THEME`: marks on a saturated fill, brand marks, the session window's own palette).
- It sets only tokens the light theme defines.
- Every text pairing reaches WCAG AA in it, in the session window too; so does each sticky colour's ink on its paper, and every ANSI colour but black on its terminal's well. Text in a filled shape reads at least as well as in the light theme, or meets AA.

Showing a second dark theme under System, rather than only when picked, is for the theme picker: System shows the one theme per mode the registry marks.

An alias follows its token unless the theme sets it too. The dark theme does where following would go the wrong way: `--scrim` and `--scrim-window` (shaded with the text colour, now light), `--zone-tab-shade` (towards the desk, not the text), `--primary-hover` and `--primary-edge` (the accent stays a fill under white text, while `--accent-strong` is lifted for text), `--flow-edge` (lighter, as drawn), `--badge`, `--severity-minor` and `--on-severity` (dark numbers on the lighter marks), and the `--zone-*-mix` percentages.

## Visual regression

`apps/desktop/e2e/visual.spec.ts` shots the app's chrome (the empty board, a busy board, the board menu open, the inbox open and the session window), a waiting tile, every tile state with a crowded tile, every character pose and each section of the component gallery (every primitive in every state). It pins `--font-sans` and `--font-mono` to fonts in the repo (`e2e/fonts`), so shots don't depend on the fonts installed, and it fails on 100 changed pixels. Baselines are per platform: `-linux` ones are the gate on the build agents. A test is skipped on a platform with no baselines. The spec's header says how to regenerate them.
