# The daemon's own git runs no hooks

The daemon runs git in agents' worktrees and the repos they share: it makes worktrees, fetches, reads status, commits a new zone's first commit, merges a crew's makers and pushes pull requests. Git runs the repo's hooks for many of these. A hook can be a file an agent wrote: with an in-tree hooks path (husky's `.husky/_`), a `post-checkout` committed on an agent's branch runs as the board makes a worktree on it. The daemon would run it with no step from the user, outside the agent's permissions.

## Decision

- **Every git command the daemon runs has hooks off** (`-c core.hooksPath=/dev/null`, which a repo's config can't turn back on). A command that wants a hook asks for it by name (`runGit`'s `hooks` option). None does today. A push to a remote that is a local folder runs that repo's `receive-pack` here, in a git that doesn't get the daemon's `-c` settings and reads that repo's own config. So the board pushes to a folder only when the user's global or system config produces its URL: as the remote's `url` or `pushurl`, or by a `url.<folder>.insteadOf` or `pushInsteadOf` rewrite to a path inside that folder: no `..` or `%` past it (git decodes `%2e%2e` in a `file://` URL), and not a sibling folder that only starts with its name. A URL that is the folder itself must be a repo, since git otherwise tries `<folder>.git` beside it. Anything else is refused, however it was named: the repo's own config, a rewrite the repo's config sets, or the old `.git/remotes` and `.git/branches` files. Anything not plainly a server (a scheme other than `file`, a remote helper's `<transport>::`, ssh's `host:path`) counts as a folder. For a folder the user's config names, `receive-pack` runs with hooks off too, but that folder's own config (its `core.alternateRefsCommand`, say) is trusted, as the user's own choice.
- **fsmonitor is always off** (`-c core.fsmonitor=false`): it is a program named in the repo's config that git runs on every `status`, and the daemon's reads don't need it.
- **No program the repo's own config names runs on the board's push or fetch.** A worktree shares its repo's `.git/config`, which an agent can write. Before a push or fetch, the board refuses when the repo's local or worktree config (or a file it includes) sets a key that names a program git would run there: `core.sshCommand`, `core.askPass`, `core.gitProxy`, `core.alternateRefsCommand`, `credential.helper` and `credential.<url>.helper`, `remote.<name>.uploadpack` and `receivepack`, `protocol.allow` and `protocol.<name>.allow` (allowing `ext::` makes a remote's URL a command), and Git LFS's `lfs.customtransfer.<name>.path` and `lfs.standalonetransferagent` (or `lfs.<url>.standalonetransferagent`). A config git can't read is refused too. The user's global and system config stay trusted. The board's pushes never sign (`--no-signed`), and its merges never sign (`--no-gpg-sign`), so `gpg.*` keys aren't refused: a repo may sign its own commits with a program of its own.
- **No merge driver or filter the repo's own config names runs as the board makes a worktree or merges a crew's makers.** A branch an agent made can carry a `.gitattributes` that picks a driver (`merge=<name>`) or a filter (`filter=<name>`), and the agent can name its program in the shared config. The board makes a worktree (an agent's, a reviewer's detached one, a crew's) without its files, reads the config git reads there, since a conditional include (`includeIf` on `gitdir:` or `onbranch:`) can apply in the new worktree alone, and checks the files out only then; a refused worktree is removed, with the branch it made. Before a crew merge it reads the crew worktree's config. It refuses when that local or worktree config (or a file it includes) sets `merge.<name>.driver`, `filter.<name>.clean`, `smudge` or `process`, or a Git LFS extension's `lfs.extension.<name>.clean` or `smudge` (which Git LFS's filter runs for a pointer that lists it), or can't be read. Git LFS's own filter, with the exact values `git lfs install --local` writes (with `--skip-smudge` too), is allowed there, as it runs the `git-lfs` on the user's PATH. But with Git LFS's filter on in any scope, a checkout downloads the objects it lacks as a fetch would, through the transfer agents, credential helpers and ssh the config names, so the keys a push or fetch is refused for are refused for the checkout and merge too. Anything in the user's global and system config stays trusted, so `git lfs install`'s global filter works as before.
- **Filters stay on.** Git LFS fills in its files at checkout with a filter, not a hook, so a new worktree still has them. Its `post-checkout`, `post-commit` and `post-merge` hooks only mark lockable files read-only, which the board does without. Its `pre-push` upload is done explicitly before each push the board makes: when the pushed commit's tree tracks files with LFS and `git lfs` is installed, `git lfs push` runs first, and a failed upload stops the push.

## Consequences

- A repo's own hooks no longer run for the board's git: a `pre-push` check on Open pull request (the board's gate is its check), or a `post-checkout` that sets up a new worktree (copying an env file, installing dependencies). An agent that needs that set-up does it itself, in its worktree.
- Commands the user or an agent runs in a worktree are theirs, and run hooks as git always does.
- A repo that sets one of those program keys in its own config (a deploy key's `core.sshCommand`, say) can't Open pull request, or start an agent from a branch the board must fetch, until the key moves to `~/.gitconfig`. The refusal names the keys.
- With Git LFS's filter on (as `git lfs install` sets it globally), such a repo can't start an agent in a worktree or merge a crew's makers either, as a checkout downloads LFS files the way a fetch does. The refusal says that is why.
- The board won't push to an origin that is a folder named in the repo's own config. A local mirror for pushes goes in `~/.gitconfig` (as `url.<folder>.pushInsteadOf`).
- A repo that names its own merge driver or filter in `.git/config` can't start an agent in a worktree or merge a crew's makers until that key moves to `~/.gitconfig`. The refusal names the keys.
- Git reads the config again as a guarded command runs, so the check alone would leave a gap: a key written into the repo's config between the check and the command. So each guarded command (push, fetch, the checkout of a new worktree, a crew's merge and its restore) runs with the programs it could run pinned, on the command line, to what the checked config gives them: the credential helpers, `core.sshCommand`, the password prompt, `core.alternateRefsCommand` (`true` unless the user's config names one, so a fetch in a repo with alternates offers fewer of its commits), `protocol.ext.allow`, the upload or receive pack, the file transport off for a push to a server (so a url rewritten since can't turn it into a push to a folder, whose receive-pack would run that repo's hooks), and, for a checkout or merge, each filter and merge driver the attributes it reads could pick, the attributes file and `merge.default`. A merge driver the config doesn't name runs as git's own three-way merge, and git's builtin names (`text`, `union`, `binary`), which a config-named driver would take over, are pinned to git's own merges too. Each driver's `recursive` is pinned, to the checked value or to the driver itself.
- What no pin can hold is checked again once the command has run, and the command then fails, saying which key came to be set: Git LFS's transfer agents and extensions, a git:// proxy when the user's own config names one (a proxy for one host leaves the others open), a filter's `process` when the user's config gives that filter a `clean` or `smudge` alone (an empty `process` would turn those off), and a filter or driver no attribute the board read picks. By then the program may have run: the failure is a report, not a guard. It sees only a key still set when it reads: a program that removes its own key before then goes unreported, so it is a tripwire for a careless write, not a guard against a deliberate one. A new worktree is removed; a pushed branch stays pushed, and the failure says so.
- The attributes are read just before the command, without waiting on a file that isn't a plain one and only as far as a size limit (a file that can't be read whole, or a search of them that fails, refuses the command), from the trees it checks out, the worktree and index, `info/attributes` and the user's attributes file. One rewritten in between, or a system attributes file, can pick a name the pins missed; the check after covers a key for it written since, not one already set in a scope the board trusts.
- `textconv` and `diff.<name>.command` aren't refused: the board's diffs list file names only, which runs neither.
- The board's status and diff reads of a worktree, and its hashing of a crew's changed files, turn off each filter program the repo's own config names (its `clean`, `smudge` or `process` as the user's own config has it, or empty), rather than refuse: a refusal there would hide every agent's changes in such a repo. A file such a filter would change may then show as changed, and a crew's commit stores it unfiltered. Git LFS's filter, as it installs itself, and every filter in the user's own config, still run; but when the repo's own config sets a Git LFS extension's program, which that filter would run, Git LFS's filter is off for those reads too.
- The restore that puts a crew worktree's uncommitted files back is refused, as a checkout is, when the repo's own config names a merge driver or filter. The refusal names the keys.
