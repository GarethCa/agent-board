# Orchestrators: an agent the user lets start, message and watch other agents, inside a scope

An agent on the board should be able to lead others, as a person does by hand with a terminal multiplexer's commands (`open`, `send`, `status`, `screen`, `close`): start a worker with a task, wait for its turn to end, read what it handed back, send a follow-up, close it. The test is whether an agent on the board could run this repo's own implement-and-review loop. This builds on ADR-0010: the same CLI, the same MCP server and the same board token, with the allowlist widened for orchestrators only. (The ticket asked for an ADR-0002 amendment; ADR-0010 is where the board token's trust model lives, so this extends that.)

## The capability

- **Per agent, and only the user's.** `agents.orchestrate` is a scope (below) the user set by hand, or null to follow the agent's zone. The user sets it with `agent.setOrchestrate` (and `agent-board orchestrate on|off <ref>` from a terminal or any shell on the board), or starts an agent with it (`agent.spawn`'s `orchestrate`). Turning an agent off by hand sets `agents.orchestrate_off`, which no zone overrides until the user turns it on again. An agent's own session is refused `agent.setOrchestrate` and `zone.configure`, so no agent lets itself or another orchestrate; a user-side session (below) may call `agent.setOrchestrate`; a zone's switch stays the app's, as every setting does.
- **By the zone, in the app.** A zone's **Let agents orchestrate** (`Zone.agentsOrchestrate`, `zone.configure`) is on by default, for new zones and, by its migration, for the zones there were: the maintainer's call, since agents leading agents is what the board is for, and one switch turns it off. A live agent orchestrates at `zone` scope while the zone its tile is in now has it on, however it came to be there: started there, moved in, or there before the switch went on (the governance review's G9; before it, only an agent the user started in the zone while the switch was on did, which was harder to explain and bought nothing the location bound didn't). Moved to a zone with it off, or loose, it orchestrates nowhere. Switched off, no agent in the zone orchestrates at its next call, and a grant by hand to an agent in it is cleared for good. An agent refused because it may not orchestrate is told why and what would change it (`notOrchestratingReason`): its zone's setting is off, it is in no zone, the user turned it off, it is as deep in a crew as an agent goes, or its session has ended.
- **Checked at every call, never cached.** The token's agent must be live, be the token's own session, and may orchestrate now. Turning it off refuses the next call.
- **Children by their zone, three deep (G10).** An agent an orchestrator starts gets `spawnedBy` set and no scope by hand, whatever the call asks (`orchestrator.spawn` takes no `orchestrate`); it orchestrates as its zone lets it, like any agent. A crew goes at most three agents deep (`MAX_CREW_DEPTH`; `agents.crew_depth`, one more than its starter's, fixed as it starts, so removing an agent between two never lowers the one below): the user's agent, the agents it starts, and theirs. The third never orchestrates by its zone, and none that deep starts another even if the user lets it orchestrate by hand, so a loop can't fan out without bound. The user can still turn any agent off.

## The user's side

- **Decide by who is calling.** `board.identify` says each token's `side` (`BoardCaller.side`). Only an agent's own session is on the agent's side, and stays so once it has ended (its connection never turns into the user's). Every other session the app starts is on the user's side: a shell tile, a tab (an agent's too), and an ended agent's fallback shell, which speaks for the agent's tile, and whatever the user runs in it by hand. A user-side session orchestrates at `board` scope, logged as that shell (an agent's pane or tab as "the agent's shell"), and the agents and edges it makes are the user's own (`spawnedBy` and `madeBy` null). It may also call `agent.setOrchestrate` (`USER_SIDE_METHODS`), but not `zone.configure`: a zone's switch reaches every agent in it, and stays the app's. It may not type into a session, answer or decide a permission prompt, or change any other setting: typing into a terminal can answer a permission prompt, and `send` covers messaging safely.
- **No token, the user.** The orchestrator methods take no token from a connection that never presented one: it is the user's, at board scope, logged as "you". So `agent-board new`, `send`, `wait`, `read`, `interrupt`, `restart`, `close` and `edge add|remove` work from any terminal, as a terminal multiplexer's commands do. This opens nothing new: such a connection already reaches `agent.spawn` and the rest. A connection that presented a token can't drop it to act as the user.
- **The trigger.** An agent ends, its pane drops into a shell, and the user starts `claude` there by hand. That `claude` inherits the shell's token. Before, it couldn't start an agent from the board CLI at all; now it acts for the user, and its own permission prompts stay the user's.
- **What it opens.** An agent that a user-side token reaches (one started by hand in a board shell) can orchestrate at board scope. That is the user's choice of what to run in their shell, as with any tool they start there. The guard is not a sandbox either way (below).

## Scope

- `zone` (the default): the agents in the zone the orchestrator's tile is in now, and starting agents there. A loose orchestrator has no zone, so it can start none without a zone in its scope.
- `repo`: the agents of its repo, wherever they sit, and starting agents in any zone of it (a repo or folder zone of it, or a group whose default repo it is).
- `board`: anything.
- Always the agents it started, wherever the user moves them: otherwise dragging a worker out of the zone would orphan it mid-loop. Never itself: `send`, `interrupt`, `restart`, `close`, `read` and `wait` on `me` are refused.
- A target outside its scope is `BOARD_ERROR.outOfScope`.
- **A reply to an agent that messaged it.** An agent that got a message from another agent, sent by that agent's own scope (`orchestrator.send`, delivered), may `send` back to it for an hour from its latest message (`reply-paths.ts`), whatever its scope says and even if it may not orchestrate: the guard lets `orchestrator.send` through for it, to that agent alone, and the method checks again. Otherwise the Captain could message a zone's orchestrator that could never answer it, and the user relayed every reply by hand. It is the one exception to both the scope and the rule below, and it opens a message and nothing more: no `read`, `wait`, `interrupt`, `continue`, `restart`, `pause`, `close`, edge or hand-off to that agent, and no message to any other. A send its scope allows is an ordinary send; only one it doesn't goes as an answer, which passes every other check a `send` makes (the text allowlist, the target between turns, no permission prompt pending) and is logged as a `send`. The path runs one way, and is kept narrow so it never outlasts its reason. An answer opens no path back, so an agent that answered once gains no reach over it: moved out of the asker's zone, it is out of the asker's reach again. It closes once the asker is let reach wider than it did as it asked (a scope by hand, or a zone's switch), so no answer goes to an orchestrator wider than the one that asked: that is why it doesn't reopen G14, as the asker chose to open the conversation at that scope, and both lines are in the activity log. None opens to the asker's own crew, which answers in its turn's last message, as it always has. The user's side opens none, having no tile to answer. Paths go when either agent is removed, and are kept in memory, so a daemon restart forgets them and the asker messages again. A message the receiver couldn't answer by its own scope ends with a line naming the sender and its ref, ``[agent-board] From <name> (agent:…), who you may answer with `agent-board send agent:… -- '…'`.``: the CLI, as an agent that may not orchestrate isn't listed the MCP's `send` (harnesses read the tool list once, as they start, so listing it would offer every agent a tool that refuses nearly every call). An orchestrator answers over the MCP's `send` too.
- **Not through a wider orchestrator.** A message runs under the permissions and the scope of the agent that gets it, not the sender's. So an orchestrator may read and wait for any orchestrator in its scope, but steer one (`send`, `interrupt`, `restart`, `close`, or an edge into it) only when that one's scope is no wider than its own (`board` > `repo` > `zone`); otherwise a `zone` orchestrator could ask a `board` one to act for it (the governance review's G14; until then it needed `board` scope to steer any orchestrator). A residual risk is accepted: a peer of the same scope also reaches its own crew wherever the user moved them, so two peers' reach isn't identical. What `zone` scope hands over is the agents in that zone as they are: messaging a user's agent that runs in a looser permission mode (auto, or bypassing permissions) runs the message under that mode. The user picks the scope knowing what is in it.

## The trust model

- **The guard stays default-deny.** `guardBoardCallers` (ADR-0010) still refuses a board token's connection every method outside `BOARD_CALLER_METHODS`, except the `ORCHESTRATOR_METHODS` (the six here, and `orchestrator.addEdge` and `removeEdge`, ADR-0012), which pass only while that connection's session may orchestrate, and `orchestrator.send` to an agent that messaged it (the reply path, above); each of them checks the token it is given again. Nothing else opens: `session.write`, `agent.answer`, `agent.decidePermission`, `agent.spawn`, `agent.delete`, `settings.*`, `zone.configure` and the rest stay refused to every agent, orchestrators included. A user-side session also reaches `USER_SIDE_METHODS` (above), and no more.
- **What the control methods do.** `orchestrator.spawn` is `agent.spawn` in a zone of the scope, without the user's own choices: another repo (`repo`), a place on the board, `allowProjectCodexConfig` (Codex project config the user must review), `issueZoneId`, and `orchestrate`. Its agents run as any agent does, in their own worktree and branch, with agent-board's hooks: their permission prompts go to the user's inbox, never to the orchestrator. `send` is `agent.answer`, only to a live agent between turns and not while a permission prompt is pending (so it never types into a permission dialog). `interrupt` is `agent.interrupt`, as Ctrl-C: on an agent that needs permission it releases the held prompt, which denies it, as Ctrl-C in its terminal would; it never allows one. `continue` is `agent.continueOnCredits` (**Continue on credits**): only to a Claude agent its usage limit stopped, it closes Claude's rate-limit menu with Escape, its cancel, picking no row (so never one that opens a billing page), and submits `continue`, the step Claude offers itself; since a `send` to a rate-limited agent is refused (its keys would land on that menu), this is the one way an orchestrator carries a crew member on past its limit, and only when it chooses to. `restart` is `agent.resume`, as the tile's Restart: an ended agent starts again in its tile, worktree and branch, carrying on its conversation; never forced, so a fallback shell running something stays the user's to end. With `fresh` it starts a new conversation instead, in the same tile, worktree and branch: Claude under a new session id (`--session-id`, since a new conversation under the old id would collide with its transcript), Codex as a new conversation. The old conversation's id and transcript path go to `agent_conversations` and show as `Agent.earlierConversations`, so its transcript stays reachable; a later plain restart carries on the new one. Its optional `prompt` is the new conversation's first message and passes the same text allowlist as `send` and `new` (refused text is logged), and is refused without `fresh`. It is scope-checked and logged as a restart, with `fresh` in the log line's detail. `pause` is `agent.pause`, marked as paused by the orchestrator, and `wake` is `agent.resume` on a paused agent only; a `send` to a paused agent wakes it with the message. Nothing pauses an agent on its own: no idle timer, no hint. `close` is `agent.stop`. With `remove` it is `agent.delete` without `force`, and only for an agent it started. Deleting an agent deletes its reviewers first, forced, which `review.start` makes for the user (`spawnedBy` null), so a remove is refused outright while the agent has a reviewer the orchestrator didn't start; `agent.delete` then checks the agent's own unsaved work before it deletes anything. So it never deletes the user's agents or anyone's unsaved work.
- **What it may type: an allowlist.** A prompt or message may hold printable characters, spaces, tabs and line breaks, nothing else (`orchestratorTextRefusal`): any Unicode control or format character (an escape, a carriage return, DEL, NEL, a zero-width or bidi mark, a line or paragraph separator) is refused wherever it is. Stripping them instead would let one hide a command (`\x01/model` types `/model` once `agent.answer` drops the `\x01`), and none belongs in a task. Then, with leading whitespace gone, it may not start as a harness command: `!` (Claude and Codex run it in a shell) or a `/command` (a built-in such as `/permissions`, `/model`, `/config` or `/approvals`, which change permission modes, models and settings), but for a namespaced `/plugin:command`: built-ins never have a colon, and a plugin's command or skill (`/mattpocock-skills:implement`) is how this repo's own loop starts its workers. A leading `#` is fine: Claude dropped its `#` memory shortcut in late 2025, and a prompt often opens on a Markdown heading. So an orchestrator can't change a permission mode or a setting, its own or a worker's, by typing.
- **Not by choosing a child's project config.** A child's worktree is cut from its base, and a repo's `.claude/` (settings, hooks), `.mcp.json` and `.codex/` set its permission mode, allowed tools, hooks and MCP servers. An orchestrator could commit looser settings on its own branch and start a child from it, so a spawn with `baseBranch` is refused when the base's project config differs from the repo's HEAD; it names the files, and the user can start that agent. The check looks at exactly what the worktree is cut from, `refs/heads/<base>`, never a tag or other ref of that name, and fails closed when git can't answer.
- **Nothing it names reaches git as an option.** A base or branch name must pass `git check-ref-format --branch` and not start with `-` (the user's own spawn checks its base the same way), and goes to git only as `refs/heads/<name>` or after `--end-of-options`. An agent's name and an issue become branches only as slugs, which never start with a dash. The project-config paths are fixed, after `--`. A `--output=<file>` base can't make git write a file. A base from a worker's branch (a reviewer of its work) passes as long as the worker left that config alone. HEAD is the user's checkout, which an orchestrator never moves through these methods.
- **Wait counts the turn it caused.** `orchestrator.wait` is event-driven in the daemon, with a timeout. An agent an orchestrator just sent a message (or started with a prompt) is "awaiting its turn" until an update shows a turn under way (`running`, `thinking`, `needs-permission`, `handing-off`) or the agent ended. Any other update (a rename, a status, the `failed` or `rate-limited` it was sent in) is no sign of it, so the state before the turn never answers the wait. A wait ends with its connection: one whose CLI the harness killed leaves nothing behind. `send` refuses an agent mid-turn for the same reason: a message queued behind a turn would make that turn's end look like the reply's. A wait gives up after 50 s by default and says so (the CLI exits 3), so it answers before the harness gives up on it: Codex gives an MCP tool call 60 s (`tool_timeout_sec`), and Claude's Bash tool a command 2 minutes. `--timeout` (or the tool's `timeout_seconds`) waits longer, up to 30 minutes, where the harness allows.
- **Read stays in the worktree.** `orchestrator.read` returns the agent's final message, or a text file of at most 256 KiB whose real path (links followed) is inside the agent's worktree.
- **The activity log.** `orchestrator_activity` keeps who, what (`spawn`, `send`, `interrupt`, `continue`, `restart`, `pause`, `wake`, `close`, `remove`), to whom, when, what it asked (the message or prompt, cut to 500 characters), and `done`, or `refused` with why, so the user sees what was tried as well as what was done. That covers every refusal of a spawn, send, interrupt, restart or close made with a live session's token: by the guard or the method to a tile that may not orchestrate (as that tile), outside the scope, with a bad id or bad params. A call with a token no live session holds has no one to log as. A log line that can't be written is logged to the daemon's log, never turns a done action into a refusal. Each line is broadcast as `orchestrator.activity` to every connection, and `orchestrator.activity` reads it, newest first, for any session: a lead may want to read a peer's log, and what it would hide is visible elsewhere (the governance review's G17; until then a session read only its own tile's lines). A tile logs at most 20 refused lines a minute, so one that loops on refused calls can't grow the log or flood the app without bound; done lines are never held back. Reads and waits aren't logged: they change nothing. Names are kept as they were, since agents are renamed and deleted. Append-only is the daemon's convention: nothing in SQLite stops an update or delete, and nothing prunes it yet.
- **Still not a sandbox (ADR-0010).** An orchestrator runs as the user and could open the socket without its token, as any agent could before. What this rules out is the board CLI and MCP offering it more than its scope: none of what they advertise answers a permission prompt, types raw keys, changes a permission mode or setting, or acts outside the scope the user chose. `agent-board orchestrate on|off` presents the session's token like every command, so it is refused in an agent's own session; a shell on the board, a terminal outside agent-board, or the app turns it on.

## Spawned-by

- `agents.spawned_by` is the orchestrator that started the agent (`Agent.spawnedBy`); `agent-board show` says "started by". Deleting the orchestrator clears it in the agents it started (they stay, started by no one now); the activity log keeps who did. The board draws an orchestrator's agents in a crew frame beside it, or with a "from" chip, and its session window has an Activity tab with its lines of the log. Asking what to do with its crew when the orchestrator is deleted is still to come.

## The surface

- **Crew events and finished, through the same wait.** Polling states was noisy: an agent whose gate runs in the background ends turns long before it is done, Claude's idle prompt moves it from `idle` to `waiting` a minute after each, and `close` makes it `done`. So `orchestrator.wait` also takes `crew` (the caller's crew as it is at each check, the agents it started and theirs; every agent for the user's side), a `finished` pseudo-state (`Agent.workFinishedAt`: the agent handed off, or set its status with `done`, until its next prompt), and `since`, a cursor: then it answers with the **crew events** after it of those agents (`turn-ended`, `finished` in place of that turn's end, `needs-you`, `not-sent` (a message typed at its prompt that started no turn, `Agent.unsent`), `failed`, `rate-limited`, `ended`, `pr-opened`), as soon as there is one. They are derived in the daemon from the `agent.updated` events every wait already hears, by comparing each with the agent's last update, so each comes once, never on a flip. Only Claude's `idle_prompt` is silent (the hook states know which notification left an agent waiting): a wait takes an agent it left waiting as `idle`, while Claude's own question (`agent_needs_input`) is `needs-you` and `waiting`. `pr-opened` is an open pull request new since the agent's pull requests were first read this run: the pull-request watcher tells the log of every read (`onRead`, with whether it was the first), so a restart's first read announces nothing, and a first read that found none (and so changed nothing, telling no client) doesn't hide the next one. An agent started this run is read as it starts, not at the next round, so a pull request it opens in a short first turn is news too; and the watcher's rounds start only once the log hears its reads, so no first read at daemon start is lost. An event keeps the crew its agent was in as it happened (its `spawnedBy` chain), so a removed agent's last events, and its `ended: removed`, still reach its orchestrator between waits. The daemon keeps the latest thousand in memory. A cursor is `<run>.<n>`, the run named afresh each daemon start: a cursor of another run (from before a restart) gets every event of the new run, marked `missed`, so a restart never silently skips events. An answer carries at most 100, the rest following from its cursor; `now` and `all` start a watch. `agent-board watch` streams them by calling the same wait in a loop; the MCP `wait` with `since` is one round of it, since a tool call answers once. Each agent named is scope-checked as for `read`. No second mechanism (a subscription, a stream over the socket) was added: one long-poll path keeps the connection-ends-it and timeout rules.
- **Its crew's status lines.** `orchestrator.setStatus` (`status set --agent <ref>`, the MCP `set_status` with `agent`) sets the status line of an agent in the caller's crew only: the agents it started and theirs (`spawnedBy` chain), a narrower rule than the scope that `send` and the rest allow, because the line is what the user reads on the tile as that agent's own. Not itself, nor an orchestrator of wider scope, and `done` stays the agent's to say. The status records the orchestrator's name as `setBy` (a snapshot: a rename shows from the next write; null for the user's side, whose line is the user's own), so the tile says who set it; the agent's own `board.setStatus` clears it, and the latest write wins. Logged as `set-status`; the user's side (no token) may set any agent's.
- **CLI** (`agent-board help orchestrate` teaches the loop): `new [--zone --name --harness --model --role --branch --base <branch or agent ref> --issue --file] <prompt>`, `send <ref> <message>`, `wait <ref>... [--crew] [--until states|finished] [--any] [--timeout s]`, `watch [<ref>...] [--crew] [--only kinds] [--since cursor|now|all] [--count n] [--timeout s]`, `read <ref> [path]`, `interrupt <ref>`, `continue <ref>`, `restart <ref> [--fresh [--file f | -- prompt]]`, `pause <ref>`, `wake <ref>`, `close <ref> [--remove]`; and for the user, `orchestrate on|off <ref> [--scope]` and `activity [--of <ref>]`. `--base agent:impl` cuts a child from its implementer's branch; with `--role reviewer` (or `follow-up-reviewer`) it is instead a detached checkout of that branch's tip, with no branch of its own, and starts with its zone's role template.
- **MCP**: `new_agent`, `send`, `wait`, `read`, `interrupt`, `continue_on_credits`, `restart`, `pause`, `wake`, `close`, listed (and one sentence added to the instructions) only for a session that may orchestrate (a shell's included) when its harness lists the tools, as it starts. Turning it on later reaches the CLI at once, and the MCP tools at the agent's next start. A harness offers the model only listed tools, so the rest of the board's agents never see them.

## Laying out its zone

An orchestrator's crew piles up where the board slots it, so it can lay out its zone too: `orchestrator.move`, `arrange`, `addZone`, `changeZone`, `removeZone`, `addNote`, `editNote` and `removeNote` join `ORCHESTRATOR_METHODS`, checked and logged as the others are (`move`, `arrange`, `add-zone`, `change-zone`, `remove-zone`, `add-note`, `edit-note`, `remove-note`); `orchestrator.map`, which reads a zone and moves nothing, is checked but not logged.

- **Through the board's own methods and rules.** Each acts through the methods the board's drags and menus call (`agent.move`, `shell.move`, `item.create`, `item.update`, `zone.addUnbound`, `zone.update`, `zone.dissolve`), placed by the board's own geometry, which moved to the daemon for it (`board-layout.ts`, `board-tidy.ts`, `board-arrange.ts`): a new tile's first free slot, a crew member's spot beside its lead, a new zone stepped past the others, a resize that packs only the tiles it cuts. A tile the board slots without saving (no place of its own yet) is worked out as the board slots it (`slotUnplaced`, which the board calls too), and a resized tile at its size from the view state. What it moves lands clear of what is there, and the zone grows to hold it; an arrange fits the zone to what it holds, shrinking it as well. No state of its own but who made a group or note, and each orchestrator's arrange settings (`by`, `layout`, `auto`), kept in the view state (`arrangeSettings`, by session id), so they need no migration.
- **What it may move.** Any tile or note in its scope or in a group it made, and itself: the "never itself" of steering doesn't apply to where its tile sits, but at `zone` scope its zone *is* its scope, so it moves itself only within it (moved out, it could neither come back nor arrange it). Into a zone of its scope or a group it made; loose on the board only at board scope. Never an agent into a zone whose switch would let it orchestrate where it can't now: that would be an agent granting orchestrating, which only the user does. For the same reason a group an agent makes has **Let agents orchestrate** off: with its crew in it, they would orchestrate where the user turned it off.
- **Bounded.** A wish (`at`) more than 1000 px past a zone's edge is put at that reach, a loose one or a new group within 100,000 px of the origin, and a group is at most 8000 px a side. A move, note or arrange that would grow its zone over another is refused before anything moves: zones never overlap. A group's name is at most 80 characters with no control character; a note's text has tabs and line breaks but no other control character, and room left under its limit for the signature. Arranges of a zone run one at a time, and an arrange keeps one item per cluster part, deleting extras.
- **What it may change.** Only the groups and notes it or its crew made (`zones.made_by`, `board_items.made_by`, migration 0048, as `flow_edges.made_by`); a zone bound to a repo is the user's, and no zone goes inside another (that needs a design first). An undo that makes one again makes it the user's. The user's side changes any group or note.
- **Arrange is deterministic.** The same board arranges the same way, whatever order the daemon lists it in, so arranging again moves nothing. It moves only tiles in scope, and the clocks it or its crew made in the zone (never the user's own: on the user's side, the clocks an agent made), which go on the top row after the shells in the order they were made; the rows keep clear of the rest. A clock it made is laid out rather than kept clear of, as one kept clear of where it was left (stair-stepped beside a tile that moved between two clocks) would decide where every lane went.
- **The board itself, at board scope.** `orchestrator.arrangeBoard` (`agent-board arrange board`, the `arrange` tool with `zone: "board"`) lays out the board as the user's **Arrange the board** does, with the same pure layout (`arrange-board.ts`): whole zones in rows a gap apart and the loose agents and shells below them, never what is in a zone. On both paths the notes, shapes and text loose on the board (turned ones by their upright box) and external sessions' tiles stay put, and what moves keeps clear of them. Only an orchestrator of the whole board (the Captain) may call it, and nothing calls it by itself: no auto-arrange runs it.
  - **An exception to "What it may change".** It moves every zone, the user's repo zones too, by their place alone (never their size or what is in them). The user can't undo it, as no orchestrator's layout change is in the user's undo history.
  - **Sizes.** The daemon lays out what it stores: each zone at its saved size, each tile at its saved size (a folded chip as a full tile). The app lays out what it draws (a zone grown round an expanded tile, a chip as a chip) so the gaps hold on screen, and saves each zone at its own size. So the two can place a board a little differently where the board draws something bigger or smaller than it stores.
  - **Races.** It runs behind every zone's arrange queue, so an arrange or auto-arrange in flight finishes first and none fits a zone from its old place. A `move` or a user's drag meanwhile isn't queued. It moves zones one at a time: if one fails partway (a zone deleted meanwhile), those already moved stay moved and the log says it failed.
- **On a grid, making room.** Automated layout keeps tiles aligned in rows and columns: a zone's grid is a column a default tile and a tile gap wide (never less than the board's 16 px dots) and a row a default tile and a lane gap tall, from its first tile slot (`gridPoint`), all at the zone's **spacing**: Compact, Normal or Roomy, each a tile gap, lane gap, padding and rail's room kept in one table (`SPACING_GAPS`, `zoneGrid`). Arrange, Tidy, a new tile's slot, `move --at`, `makeRoom`, sizing a zone round its tiles and the map's lint all use the zone's own; Normal's are the numbers a zone always had. Arrange lines compact tiles up on its columns in every mode, but lays out in px: a lane or row is as tall as what it holds, a wide tile (resized, or expanded) is as wide as it is and spreads only what follows it in its own lane (by role or state, in its column of every row), a tile gap past it, and a row pushed past an obstacle goes just below it. So a tile is on the grid across, or packed a tile gap (or a rail's room) past another; down, lanes go where the heights above them put them. The map's lint holds each tile of the crew to where an arrange as set would put it now (which never depends on where things are, so only a tile moved off its place is named), and one no arrange places to the grid. `move --at` lands exactly on the grid column nearest the wish, in the nearest grid row or row of tiles already there (a lane laid out in px), and `move --near` exactly beside: what is in the way moves aside instead of the thing moved drifting off (`makeRoom`: right along its row, a whole column at a time, left to right, so a row keeps its order, with a hard cap per search). Only what arrange may move moves aside: shells, agents in the orchestrator's scope, and notes and cards it or its crew made. The user's notes and cards, a tile outside its scope, or an external session's tile where it would land refuse it, as arrange keeps clear of them. Loose on the board, with no grid, a move still lands the least distance clear. A reviewer joining its cluster, and `note add` and `note edit`, wait their turn with the zone's arranges (one layout queue per zone), and each writes a sticky's generated text only after reading it afresh, so none writes over another's note or the user's edit; a join that fails leaves the reviewer, started all the same, where the board slots it, and the daemon logs why.
- **One lane per unit of work.** By issue, each issue (or set of agents joined by edges or sharing the ticket their branch is named for) is a lane (a cluster) with no box or group zone round it. In rows, the default, a lane is a row: its text label in the first column, then a column per slot (implementer, then reviewer, then follow-up reviewer, a slot as many columns wide as its fullest lane needs and none for a slot no lane uses, so compact lanes' tiles line up on the grid, and a rail or a wide tile spreads only its own lane), then its note, saying what each agent is doing, in a cell of its own right after the lane's last tile (a short lane leaves no run of free slots before it, so its notes don't line up: no big gaps wins over aligned notes); lanes go in the order their work started, so a new one goes last; the orchestrator and the zone's shells share the top row. In columns a lane is a column, and in cards a block flowed two or three across, a free grid column and row between blocks; in both its label and its note share its first cell. Each layout maps lanes to cells, laid out in px from the sizes of what they hold, compact cells on the grid (`board-arrange.ts`), never from the agent. It makes no link card for its pull request: each tile's PR chip shows it, and the next arrange deletes any card an earlier one made (crew-made link items with an `arrange` key). Wherever an edge joins two agents, exactly a rail's room (the zone's spacing's, `RAIL_GAP` at Normal) is left past every tile the rail runs by, in that lane only (by role or state in every row, so a reviewer stays under what it reviews), and above every row it crosses; as a grid, a unit of work whose tiles any edge joins (by issue its issue's row, else its chain; the lead too when an edge joins it) is laid out exactly as rows would lay it out, from the top, and only the tiles no edge joins fill the grid, round it: clear of its tiles and of the box round each two its rails join. The grid lays out no graph of its own; a hub's rails to tiles past its neighbours cross them there as they do in rows. So the rail is at least `--rail-token-room` long beside each tile it passes, and its token and label clear every tile, whichever end the token is at; the daemon's `RAIL_TOKEN_ROOM` holds the same number and a test keeps them equal. A reviewer always follows what it reviews (`reviewOf`, or the branch it reviews), whatever their roles; agents joined both ways by edges go implementer first, then in spawn order. Without an issue, the label is its branch's ticket, else the words its agents' names start with, else its implementer's name. The label and sticky are ordinary items marked as made by the orchestrator and tagged with their cluster (`data.arrange`; the sticky also with its members and the text the arrange wrote), so the next arrange moves them with their cluster (they are anchored to it, never placed on their own), leaves alone what is already in place, and removes those of a cluster that has gone. A cluster whose key changed (its first tile went, or an edge now leads into it) takes the sticky of the gone cluster that shares an agent with it. A sticky anyone has edited keeps its text and is never deleted: one whose cluster has gone is parked, and where it can be parked nowhere the crew is laid out round it. One from before arranges recorded what they wrote counts as unedited while every line is still an agent's name and state, so it is written again or, its cluster gone, removed. Arranged by role or state, or as a grid, an arrange by issue's parts are parked rather than going: beside the crew, else below it where beside would grow the zone over another, else left where they are. A reviewer an orchestrator starts on a clustered agent's branch joins that cluster straight away, after its row, and its sticky; a sticky note added near a clustered agent, with no side, is added to the end of its cluster's sticky, never in place of what it says, and near any other agent it may move takes the slot before it (as an agent note, from an agent). Notes an agent writes are signed 🤖 with its name and the time, signed again on each edit. Folding finished agents into chips is a follow-up.
- **Seeing the layout, and keeping it.** `orchestrator.map` reads a zone as its lanes, with a lint of overlaps, the widest gap in a lane, the space between lanes, a label far from its tiles, a zone mostly empty (bigger than an arrange would fit it, or with a band of grid columns or rows right across it holding nothing, so a tile at a far corner can't hide the empty space), and tiles not where an arrange as set would put them now (one no arrange places, off the grid) or out of their lane (`zone-map.ts`), rendered as a lane table or, with `--boxes`, a box picture; an arrange prints it, so the agent checks its layout as text, with no screenshot. An orchestrator whose settings have `auto` on has its zone arranged again after every agent it starts, note it adds and agent it closes, in the zone's layout queue, logged as an arrange; a failure is only warned of. Settings an arrange asks for are kept only once nothing can refuse it: its zone is in scope and passes the growth check.
- **A picture of a zone.** The text map stays the way to check a layout; `orchestrator.screenshot` (`agent-board zone screenshot [--out] [--style]`, the MCP `zone_screenshot` tool) is for when the agent must see it. The daemon draws nothing: it sends `capture.requested` (with a deadline) to the one connection that called `capture.serve` (the app, on each connection), and waits for `capture.deliver` or `capture.fail`, at most `captureTimeoutMs` (15 s by default, under a harness's minute for a tool call); with no app connected it fails at once ("the app isn't open"), and never opens one. The app draws the zone, with a 40 px margin for its tab, in a hidden board window that paints offscreen, at 1×, or smaller for a frame over `MAX_CAPTURE_SIDE` (1,568 px) a side. What that window shows is decided in one place (`capture-mode.ts`) and is off by default: the board's canvas alone, holding the zone, what is in it and the edges between those; no chrome, panel, dialog, session window or dock, and anything else outside the canvas is invisible. An expanded tile shows "terminal hidden" in place of its terminal, always. Its preload passes on only the calls that read the board (`CAPTURE_READS`), so it never saves the user's view or windows, attaches to or resizes a session, or takes a request meant for the board's window. It is captured once it has settled: its nodes measured, then several frames with no node added, removed or resized and no edge rerouted (at most 5 s). The app takes one picture at a time, gives up before the deadline, drops a request already past it, closes each window whatever happens, refuses a window the system made a different shape from the frame rather than stretch it, and draws a PNG over `MAX_CAPTURE_PNG_BYTES` (3.5 MB, under the 5 MB a model's API takes) smaller until it fits, the scale in the answer saying so. The `lofi` style is a plain SVG the daemon draws from the map (`zone-sketch.ts`: boxes, names and states, edges and connectors as straight lines), which the app shows as an image, in a bare window with no script, and captures at its first paint. The MCP tool answers with an `image` content block and a caption (the zone's size, the scale and the map's lint line): about 2–3k tokens. The scope check is `map`'s: a picture only of a zone the agent may already read. Nothing is kept, so no migration.
- **Sizes as the app draws them.** The daemon's sizes are estimates where the app's drawing decides (an agent note's height for its text, a text item's size) and positions are saved ones where the app draws a tile elsewhere (pushed aside by an expanded tile, which is view-only). So the app's window in front says how it draws the board (`layout.measured`), a moment after it changes: every tile and item drawn other than saved (by key, with the saved box it was measured against), each agent note's height for its text (with a fingerprint of that text; measured out of sight, at the note's width and in its look, whether the board draws the note or not, as it draws only what is on screen), and the tiles expanded as it drew them. Only the app's connection, the one that serves captures, may say it. Each report replaces the last, is kept in memory only and is dropped when its connection closes; main says it again once it serves captures after a reconnect. Each measure holds only while what it was measured under is as it was: the thing's own saved box; for a note, its text and width (and in the app, the look notes are drawn in, the question it answers and the edits it suggests); for a spot an expanded tile pushed it to, the expanded tiles themselves, saved where they were at the same sizes, so a tile that collapses, moves or resizes puts its neighbours back where they are saved, with no word from the window. A neighbour pushed along by a tile that moved for another reason may be mapped a moment where it was drawn, until the window says otherwise. What is put beside a tile (`near`: a move, a note, a shape or a diagram) goes beside it where the app draws it, so beside an expanded tile the board drew clear of something is beside it on screen, not beside where it is saved. Arrange lays out round items at their drawn size and sizes each lane's note to its measured height, shorter as well as taller than the estimate. A lane's agent note about to say something new says it first, in place, and arrange waits for its measure (1.5 s at most) before laying out; a new lane's note, or an old sticky's that gives way to one, is estimated, as nothing else is written before the arrange is sure to go ahead, and a refused arrange puts back what the notes said (unless the user edited one meanwhile) and their widths and heights (a width or height the user gave one meanwhile stays; a height the app grew it to, to show the new text whole, does not), so it leaves the zone as it was. What it writes first is what the arrange itself would write, its own text, so the next arrange keeps the note current. The zone map draws things where the app does, so its overlaps and pictures match the screen, but holds the lint (grid, lanes, gaps) to saved spots. A window no longer in front says so (`away`), and nothing waits on it until it is in front again. With no window, a window away, or a note not measured in time, both fall back to saved sizes and estimates and say `unmeasured`. A capture window never reports.
- **Surface.** `agent-board move|arrange|zone|note` (with `zone map` and `zone screenshot`) and the MCP tools `move`, `arrange`, `map`, `zone_screenshot`, `add_note`, `edit_note` and `remove_note`; groups are the CLI's alone.

### Drawing diagrams

An orchestrator draws a diagram when the user asks for one, as it puts notes on the board: `orchestrator.addShape`, `editShape`, `removeShape`, `connect`, `editConnector`, `removeConnector` and `addDiagram` join `ORCHESTRATOR_METHODS`, checked and logged as the layout methods are (`add-shape`, `edit-shape`, `remove-shape`, `connect`, `edit-connector`, `remove-connector`); a `connect` line names both its items. Nothing prompts it to draw: the tools are there for when it is asked, as the harness offers its own (no more than the harness does).

- **Shapes are placed as notes are.** A shape goes where `note add` would put a note (its zone, `--at`, or beside `--near`, what is in the way moving aside), sized by the daemon for its text from character counts, about; the board grows it taller to fit as it draws it, as it does a shape the user types in. Its data is a whole shape's (`newShapeData`, the protocol's, which the board's toolbar makes its new shapes from too). Adds and edits wait their turn in the zone's layout queue, as notes do. Only a Class and a box Interface (`SECTIONED_SHAPES`) take attributes and methods; another kind refuses them, a shape changed to one drops its sections, and one changed into one takes its mono. `shape remove` removes a shape with every connector joined to it, the user's too, as removing a note does: the agent can't remove the user's connector on its own, but it goes with the shape it is fixed to.
- **Connectors join items in reach.** `connect` joins two board items in zones it may lay out (loose ones at board scope), whoever made them, since a line changes neither. Its relation is one of the board's (`RELATIONS`, moved to the protocol so the daemon and the Relation picker share it), read from `from` to `to`; its sides face each other across the axis the two are furthest apart on. Labels have tabs and line breaks but no other control character.
- **What it may change.** Only the shapes and connectors it or its crew made: shapes by `board_items.made_by`, connectors by `connectors.made_by` (migration 0062, a nullable column, as 0048). The user's side changes any.
- **Reading them back.** The board read (`tree`, the `board` tool) gives a shape's kind, text and section counts, and lists each connector under its `from` end's zone with a `connector:` ref, its ends, relation and labels; `show` prints a shape's sections and connectors, and a connector's every field. `zone map` (the `map` tool) ends with a summary of the zone's diagram, kept short whatever its size: each shape by its kind, text and section counts, and each connector, at most 40 lines; with `--sections` (`sections`), a class's members too, 12 lines a section, each cut to 80 characters, at most 200 lines. MCP has no `show`, so that is an MCP agent's read of a diagram. `arrange` prints the lanes alone, never the diagram.
- **Mermaid in and out.** `orchestrator.addDiagram` (logged as `add-diagram`) draws a Mermaid flowchart or class diagram whole: read by `mermaid.ts`, laid out in ranks as Mermaid draws one (a parent class above its children, a whole above its parts), and placed as one block where a note of its size would go, each shape and connector marked as its own, to change as any it drew. The same module reads a Mermaid paste on the board and writes a selection's **Copy as Mermaid**, so the two draw a diagram alike, and an export reads back as what was exported. It is a hand-written reader of the two grammars' common lines (node brackets and `@{ shape: … }`, links and their labels, class blocks, member lines, annotations and relations with their multiplicities, `style … fill:`), not Mermaid itself: Mermaid's package draws SVG in a browser and is megabytes, and the board needs only its structure. What it can't read, and what has no board counterpart (classDefs, clicks, notes, a subgraph's box), it passes over, and says so, on a paste too. It is bounded so no text can stall the daemon or the window: at most 80,000 characters and 5,000 to a line, links found by a scan rather than a backtracking pattern, at most 200 shapes and 500 links (each pair joined the same way once), the count of the rest reported. Control characters other than a tab or a line break are dropped from what it reads (an entity too), and `diagram add` refuses raw ones, as `shape add` does; it checks every shape as the board will store it before it makes any, and takes back what it made if a create still fails, so a diagram is drawn whole or not at all. Export reads the stored fill's slot back as the slot's colour, so a re-import keeps it; it leaves out what Mermaid can't say (a flowchart's end labels, outlines, text style) and writes a kind of shape Mermaid lacks as its nearest, or a rectangle. A read of the board's diagram as Mermaid is `diagram export`, a CLI read that changes nothing, so it is not an orchestrator method.
- **Surface.** `agent-board shape add|edit|remove`, `connect`, `connector edit|remove`, `diagram add|export`, and the MCP tools `add_shape`, `edit_shape`, `remove_shape`, `connect`, `edit_connector`, `remove_connector`, `add_diagram` and `export_diagram`.

## Named roles and the app's default roles

An orchestrator starts agents that are neither implementers nor reviewers (a designer, a researcher), so `new --role` takes any name: a built-in role's name (in any case) is that role, any other a custom role of that name, kept on the agent (`agents.role_name`, migration 0050) and shown on its badge. One field rather than `--role custom --role-name x`, which could disagree. Reviewer behaviour stays with the built-in reviewer roles. A named role's template is its zone's for the name, else the app's **default role** of that name (`default_roles`), else none. `orchestrator.roles`, `setRole` and `removeRole` join `ORCHESTRATOR_METHODS` (the last two logged as `set-role` and `remove-role`), as `agent-board roles` and the MCP tools `roles`, `set_role` and `remove_role`: a template is a prompt every zone's agents start with, so editing it is an orchestrator's act, in the log like the rest. Two guards follow from that. The app's list reaches every zone, so only a board-scope orchestrator (or the user's side) writes it; a zone- or repo-scope one writes only a zone in its scope's template for a name (`zoneId`, `--zone`), as it may reach no further. And a named role's template becomes the start of another agent's first message, so it passes `orchestratorTextRefusal` as a prompt does: when it is saved (by an orchestrator, or the zone's dialog) and again, filled in, when an agent starts with it, so one written before the check, or by hand, is refused too.

## Considered options

- **A separate MCP server or `agent-board ctl`** (the ticket's first sketch): rejected for the decision that this is the orchestration layer of the same board MCP and CLI. One token, one guard, one help.
- **Listing the control tools to every agent and refusing them in the handler**: rejected. It costs every agent tokens for tools it can't use, and advertises control to agents that don't have it (ADR-0010's rule).
- **Polling for wait in the client**: rejected. A fast turn's running state can come and go between polls, and the idle before a turn would answer a wait made straight after a send.
- **Refusing every leading `/`**: rejected; it would refuse the plugin skills this repo's loop starts its workers with. **A list of dangerous built-ins**: rejected as one that goes stale with each harness release. **Stripping control characters and checking what is left** (the first round): rejected in review, since a denylist of what to strip has to match every layer that strips; refusing them is simpler and leaves nothing to match.
- **Letting `orchestrate on` skip the board token in a shell tile**: rejected. The CLI would then offer an agent the way to turn itself on. The governance review opened it to shells by the daemon's own check of who holds the token instead, which an agent's own session still fails.
- **Children that never orchestrate** (the first rule): replaced after the governance review by the depth cap, so a lead's lead can delegate a sub-crew, and the cap still bounds a loop.
- **A shell's agents marked as started by that shell** (the governance review's sketch): rejected. `spawnedBy` names an agent everywhere it is read (crews, `show`, removal), and a shell acts for the user, whose agents have none.
- **Letting `close --remove` delete any agent in scope, or force it**: rejected. Removing is for cleaning up after itself; the user's agents and unsaved work stay the user's to delete. The user's side removes any agent, as the user does in the app, never forced, so unsaved work still stands.
- **A zone grant that follows the agent** (the scope alone deciding, as for a grant by hand): rejected. An agent the zone let orchestrate, dragged into a zone that doesn't, would orchestrate there; the zone's switch must grant nothing outside the zone.
- **A zone setting off by default**: the first call, since an agent starting agents spends tokens without asking. The maintainer changed it to on: the switch is one click away, and a refused agent says where it is.

## Starting one from New agent, in the repo's own checkout

The user starts an orchestrator from New agent by choosing the Orchestrator role (a named role, `orchestrator`, with a template of the app's own until a zone or the app saves one). The dialog starts it with `orchestrate: zone`, fills the task from the template (sending `noTemplate` so it isn't added twice), and adds a Checkout row: **main checkout** (the default) or a new worktree. This amends "every agent gets a worktree": `agent.spawn` takes `checkout: 'main'`, which runs the agent in the repo's own folder on the branch checked out there. No worktree or branch is made, `ownsWorktree` is false, and deleting the agent leaves the checkout as it is. Only the user's own `agent.spawn` takes it; `orchestrator.spawn` has no such field, so every agent an orchestrator starts still gets a worktree of its own. A reviewer, a `branch` and a `baseBranch` don't go with it. A dirty or off-branch checkout does not stop it: the agent starts all the same, but the Checkout row and the orchestrator's tile warn ("main checkout has uncommitted changes", "main checkout is on `<branch>`") while the checkout has uncommitted changes or is on a branch other than the repo's default (`origin/HEAD`, else `main` or `master`). The warning is read with `zone.checkoutState`, which only reads, and the tile re-reads it every few seconds. A second orchestrator in a zone is allowed, and so is a second agent in the same checkout; they then share one working tree (and the user's editor may too), which no worktree does.

A group with no repo (no default repo, and none given) is a third case, for an orchestrator or any agent started there: it runs in the group's own folder, outside git, which the app makes in its data directory (`<data dir>/groups/<zone id>`) on first use and keeps across restarts. No worktree or branch is made, `ownsWorktree` is false and `plainFolder` true, and the app runs no git there: no branch reads, pull request lookups, gate, checkout warning or review of its work. A `branch`, a `baseBranch` and a reviewer are refused, as there is no repo to cut from. Deleting the agent leaves the folder, which the group's other no-repo agents share. In New agent the Repo field offers **No repo** for such a group, which the Orchestrator role starts on until the user picks a repo, and the Checkout row then says where it runs instead of offering a checkout. An orchestrator there picks a repo per task: `orchestrator.spawn` takes `repo` (`agent-board new --repo <path>`, the MCP tool's `repo`) in a group, cutting the agent's worktree from it, and refuses it in a zone bound to a repo; with none, the agent runs in the group's folder too. This amends the "every agent an orchestrator starts gets a worktree" above for such a group.

A reviewer an orchestrator starts with `--base agent:<ref>` in a group is cut from that agent's repo, unless given another with `--repo`: in a group its agents each have their own. `plainFolder` is kept in a column (`agents.plain_folder`), set as the agent starts; agents started in the app's own group folders before the column are still known by their path (inside the data directory's `groups`). The folder stays when its group is deleted, like the group's agents' own folders do. The group's no-repo agents share its folder, and so its `.agent-board/` files and the harness's per-folder state (Claude's project history, its resume list); for that reason a plain-folder crew member's plan and a question too long for a flag go to the user, not its orchestrator, as an agent with no worktree of its own always has.

A group's folder may also be one of the user's: a zone added for a folder outside git is a group whose own folder (`zones.group_folder`) is that folder, and its agents with no repo run there, as plain-folder agents, in the same way. Deleting the zone leaves the folder. A repo with no commits yet gives a new agent a worktree on a branch with no commits (ADR-0007), or, on a git too old for that, the repo's own checkout. That fallback amends "an orchestrator's agents each get a worktree of their own" too: no worktree can be made for any agent there, so an orchestrator's agent works in the checkout like the user's own would, rather than not starting.

An agent in the repo's own checkout owns no branch (`Agent.branch` is empty, as for an agent adopted in a folder of the user's), whatever is checked out there. So it never opens a pull request or merges: `gate.openPullRequest`, `board.openPullRequest` (the CLI's `open-pr` and the MCP tool's), and `gate.merge` refuse it, saying to make a branch in a worktree first or to have an agent it starts do the work, and the app shows no Open PR or Merge for it. Deleting it, closing it with `remove`, restarting it and a merge's clean-up leave the folder, its files and its branch as they are, and `removeWorktree` refuses to remove a repo's own checkout.
