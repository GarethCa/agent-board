# Schedules are clocks on the board

A schedule used to be a row per agent (`schedules`, keyed by its session), shown only as a chip on the agent's tile and made from the tile's ⋯ Schedule…. The user wanted a schedule to be an object on the board, joined to an agent, that can also start a fresh agent for a task, wait for it to finish and close it. Two ways in were decided, for now, with either to be dropped later as a small change: every schedule is a clock item, and the tile's Schedule… stays and makes the clock beside its tile.

## A clock is a board item

- **The schedule is the item's data** (`ClockData`): its cron, whether it is on, what it does (`message` the agent it is joined to, or start a `fresh` agent), the prompt (what it sends, or a fresh agent's task), a fresh agent's harness, model, role and whether it closes once done, where a fresh agent's result goes, and whether it is drawn folded. So a clock moves with its zone, copies, undoes and deletes as every item does, and nothing else holds a schedule. The item store checks the data (`items.ts`), the cron included.
- **What it is doing is not item data.** When it next fires and its runs (`ClockStatus`) change as time passes, not as the user edits: a clock firing would otherwise write its item, and undo would send stale data back. Runs are rows of `clock_runs`, keyed by the clock's id with no foreign key, so a clock's history comes back when its delete is undone. Clients hear `clock.updated`, and `clock.list` gives them all.
- **The scheduler (`schedules.ts`) keeps its loop** (the plan, the timer at most a minute away, one late fire for times slept through, following clock and time-zone changes), now keyed by clock. It plans only a clock that can fire: on, with a prompt, and joined to an agent (`message`) or in a zone (`fresh`). It replans a clock whenever its item is made, changed or deleted; one still planned on the same cron keeps its fire time, so a drag or a fold as it falls due loses no fire. A clock whose last run is still going skips, saying so.
- **A run of skips is counted, and a stuck turn is flagged.** A clock's status gives the skips its latest runs are, one after another since its last run that was not a skip (`ClockStatus.skips`: how many, since when, and each reason once), so `schedule list` says `skipped ×8 since 16:00 (still working, waiting for you)` rather than only its last outcome, and the clock's card says it once its agent's turn looks stuck. A check-in can never reach an agent whose turn hangs, which is when it is needed most. So once `STUCK_CLOCK_SKIPS` (3) or more skips in a row are all because the agent it messages was still working or waiting for you, at least one of them still working (a hung turn can flicker between the two), the daemon sets that agent's flag (ADR-0016) once for that run of skips: how long it has been working, at least, without a turn ending, and that its check-ins are being skipped. It reaches the user, or the agent's live orchestrator, as any flag does. A flag the agent already has is left alone, and that run of skips doesn't raise one later, once the user has looked. The clock's own flag goes when the agent's turn ends, a check-in reaches it, or the clock is deleted, turned off or joined to another agent, unless the flag was replaced or cleared meanwhile. Which flags a clock raised is kept in memory: after a restart, a run of skips that goes on raises it again. The clock still only skips: it doesn't interrupt the agent or queue the message.
- **An agent's schedule is derived** (`Agent.schedule`): the clock that messages it, the soonest of several. So the `scheduled` state, the tile's clock chip, and the daemon staying up for one all work as before. *Amended:* an agent with one was once never stopped by restart, left for its clock to relaunch, but a clock may not fire for days (a yearly one, its day gone by, never), so a restart left the Captain and orchestrators with clocks ended, skipped by Resume all and by the restart after an update. It is now stopped by restart like any other agent, and resumed with them; a clock that fires while it is still stopped relaunches it, as before. `agent.setSchedule` stays, as a façade over that clock: it makes one beside the tile, changes it, or deletes it.
- **Existing schedules moved over** in the migration that made `clock_runs`: one clock each, joined to its agent, 60 px left of its tile in its zone (on its right when there is no room in the zone; a tile loose on the board always has room), as the tile's Schedule… places one, its runs with it.
- **Deleting an agent leaves its clocks**, unjoined: the clock says it is not set until it is joined to another agent. A schedule used to go with its agent; a board object going because something else did would surprise.

## A fresh agent's run

- **It starts as the user's agent** (no `spawnedBy`), unless an orchestrator made the clock (below), in the clock's zone, under the clock and clear of the tiles there, named from its task and the run's number (`Deps check #12`), with its harness, model and role. A clock starts none while three it started are still on the board, so kept agents don't pile up.
- **Its run ends when its first turn ends** (its `Stop`), the same moment Ask Claude's answer lands, unless its last message asks the user something (its last paragraph has a question mark, the rule that makes a scheduled agent `waiting`): then it stays open and shows `waiting`, as a scheduled agent that asks does (in the needs-you inbox when that shows every turn), and the run goes on until a turn ends that doesn't ask. Its state alone can't say so as the turn ends: Claude's `Stop` leaves it `idle`. `Agent.workFinishedAt` was not used: an agent sets it only by handing off or saying it is done, which a plain task never asks for.
- **Its result** is its final message, kept in the run's row. A per-clock setting also leaves it as an agent note where the agent's tile was, or hands it to another agent as a hand-off would (`agents.deliver`), before the agent is closed.
- **Closing it never throws work away.** It is deleted as `agent.delete` without force does; if that is refused for unsaved work, it is stopped instead and the run says it was kept.
- **A run fails** when its agent fails, ends, or is removed before its turn does, or can't be started. A fresh agent that flagged the user is kept, not closed (below).
- **A run the app stopped during** says so (`the app stopped during its run`), not that its agent failed, once the app is back; its agent, stopped by the restart, is then closed as the clock says, as at the end of a run. One whose agent was still being made says the app stopped as it started; an agent made in that moment is left on the board, not matched to its run.

## After each run: hibernate, close or leave idle

*Amended:* a clock can run a long watch (check Slack every hour, keep up with pull requests waiting on approval) without holding an agent's session open between runs. So each clock says what happens to its agent after a run, one of three modes (`ClockMode`, read from the data by `clockMode`):

- **Hibernate**: it messages the agent it is joined to and, once that run's turn ends, pauses it (`agents.pause`, by the user, as Pause does), keeping its conversation. The next run wakes it in that conversation (`claude --resume`, `codex resume`) with its prompt as the first message, as a scheduled run to a paused agent always has. Stored as `does: 'message'` with `hibernate: true`.
- **Close**: a fresh agent each run, closed once done (the `fresh` mode, as before; keeping each run's agent stays a setting under it).
- **Leave idle**: it messages the agent it is joined to and leaves it at its prompt (`does: 'message'`, `hibernate` false or missing, as every older clock is).

The mode is item data, so an older daemon reads a hibernating clock as one that leaves its agent idle, which is safe.

- **A message's run waits for its turn.** A run that sent a message used to be over as it was sent (`started`). It now goes on until the turn that message started ends, as a fresh agent's run does: that turn's final message is its result, and when it ended its `finishedAt`. A turn that ends asking the user something keeps it open until one ends that doesn't. Its outcome stays `started` while it waits (`awaits_turn` set, `finished_at` empty), because a daemon from before this settles only `running` runs and would close the agent of one as it starts up. A message queued for an agent not yet up is a run too, until the turn it starts once the agent is up ends. A fire while a message is still being typed at the agent skips (`a message is being sent to it`): that message's turn is its run's. A message that turns out not typed, as the agent went to work before its turn in the queue came, fails its run, saying so. A turn that ends any other way than its harness's `Stop` (interrupted, failed, rate-limited, or found over with no word from its harness) fails its run, so the agent's next turn, the user's own perhaps, is never taken as the run's, and a hibernating clock doesn't pause the agent under the user. One whose turn never ended at all fails once the next run fires, which sends its message as usual.
- **A run that flags the user says so** (`ClockRun.flag`): the flag its agent raised (`needs_you`) after the run fired, recorded as it is raised; a flag the agent already had as it fired, and a clock's own stuck flag, aren't the run's. A pause ends the agent's session, and its flag with it, so a hibernating clock leaves an agent whose run flagged the user up, its run saying `not paused: it flagged you`; and a fresh agent that flagged the user is kept, its run saying `kept: it flagged you`. The user sees the flag in Needs you and decides. A run that doesn't flag is quiet: a hibernated or scheduled agent is never in the inbox, whatever it shows.
- **A messaged agent's earlier failed turn doesn't fail its run.** Only a fresh agent's `failed` state fails its run; the agent a clock messages may still show a failed turn from before the run. Its agent ending, or being removed, still fails it. A message's run the app stopped during fails saying so, and its agent, the clock's own, is never closed for it.
- **A clock that starts its own agent** (`startsAgent`): a hibernating or leave-idle clock in a zone, joined to no agent, is set only when it says so. Its first run starts its agent as a fresh agent's run does, joins it (the clock writes its own item once, `agent` set and `startsAgent` cleared, so undo sees it as an edit), and from then on hibernates or leaves idle that agent as its own. Without the setting, deleting an agent would leave a clock that starts a new one at its next fire time, against "Deleting an agent leaves its clocks, unjoined". That first run is marked on its row (`clock_runs.joins`), and the run, not the clock's data, decides how it ends: it settles as a message's run does, though its turn ends before the join is written, or the write fails.

## An agent's own clock

*Amended:* a long watch is best judged by the agent keeping it: nothing left to watch until Monday, every pull request merged, a fresh look wanted each morning. So an agent may change its own clock, and no other.

- **Its own clock** is one that messages it, or whose run started it (a fresh agent, while its run lasts). Only its own live session acts as it: the board token, checked as `board.identify` does, and never a shell or an ended agent's token. A clock it names that isn't its own is refused, saying whose it is; with none, or more than one and no name, it is told so.
- **What it can change** (`clock.self`; the CLI's `schedule set|stop`, the MCP's `clock_set`): the mode (`--after hibernate|close|idle`), or turn the clock off (`schedule stop`). Not the cron, the prompt or the agent joined, and it never turns a clock on: only the user does. Each change needs a reason (`why`, at most 200 characters).
  - Set to close, the clock starts a fresh agent each run, and messages no one: the agent it named stays in its data, so setting the mode back joins it again. During a run, the agent is closed once that run is over, unless it flagged the user or the clock keeps each run's agent, as a fresh agent is.
  - A fresh agent that sets hibernate or leave idle is joined to it, and its run ends as a message's run does, with no note or hand-off.
- **Each change marks the clock** (`modeSetBy`, `stoppedBy`: who, why and when), so the card can say the agent did it and why. The marks are item data, so undo brings them back with the change. The user setting the mode again, or turning the clock back on, clears the mark (`items.ts`); any other edit keeps it.
- **Each change is kept** as a row of `clock_changes` (the run it came in, who, what and why) for the clock's history, in `ClockStatus.changes`. They aren't in the activity log: the clock's history is where the user looks for them.
- **An agent adds a clock of its own** with `schedule add --self` or the MCP's `clock_add` (`clock.addSelf`), beside its tile, hibernating it or leaving it idle. Any agent may, not only an orchestrator: `orchestrator.addClock` needs the right to orchestrate, and a clock that messages only its maker reaches no other agent. It is marked as made by no one, as the clock the user gives an agent from its tile is: set to close, it starts the user's agents, and keeps running once the agent that added it is closed.

## Clock templates

*Amended:* the same long watch is wanted in more than one zone (a Slack watch, a pull-request watch), so a clock can be saved under a name, as a **clock template**, and new clocks started from it.

- **A template is its own row** of `clock_templates` (name, unique whatever its case; data; who saved it), not a board item: it belongs to no zone and is never drawn. `clockTemplate.updated` sends clients the one template saved, and `clockTemplate.removed` the id of one removed; a client reads the rest with `clockTemplate.list`.
- **What it keeps**: the cron, prompt, mode (`does`, `hibernate`, `startsAgent`), a fresh agent's settings and where its result goes. Never the agent it messages, a hand-off's agent (a template's result is history or note) or anything of a run: those belong to one zone's clock. Its data is checked as a clock's is.
- **Starting a clock from one** (`template` on `clock.add`, `orchestrator.addClock` and `clock.addSelf`; the CLI's `schedule add --template`, the MCP's `add_schedule` and `clock_add`): the data given over the template's. Nothing ties the clock to the template after, so changing or removing a template changes no clock.
- **Who saves them**: the user (the editor, a shell, `schedule template save`) and any agent (`schedule template save|list|remove`, the board token checked as for an agent's own clock). Saving under a name already used replaces that template. An agent replaces or removes only templates it saved; the user any. An agent's session that has ended saves and removes none, whether it gives its token or its connection holds it. Every agent has the template tools, in the CLI and the MCP (`save_clock_template`, `list_clock_templates`, `remove_clock_template`, beside `clock_add`), so it can build one when the user asks.
- **Limits**: an agent saves at most 50 templates, and the board keeps at most 200; a save past either is refused, saying how many there are and how to remove one. Saving over a template is never refused. An agent's saves and removals, and those it was refused, are lines of the activity log (`save-clock-template`, `remove-clock-template`), as its other board changes are; the user's aren't.
- **A clock that hands off** is never saved as a template: `--from` such a clock is refused, saying to save its cron and prompt with `--result history|note`.

## Orchestrators

`agent-board schedule add|list|remove` and the MCP's `add_schedule`, `list_schedules` and `remove_schedule` reach `orchestrator.addClock` and `orchestrator.removeClock`, logged as `add-clock` and `remove-clock`. The agent a clock messages, a fresh agent's zone and a hand-off's agent must each be in the caller's scope; a clock is marked as made by its caller, and only its crew (or the user's side) removes it. A fresh agent an orchestrator's clock starts is in its crew (`spawnedBy` the orchestrator), so it is no shallower in the crew than one the orchestrator starts itself, and `MAX_CREW_DEPTH` holds: a clock can't give an orchestrator at the limit agents that orchestrate. Once that orchestrator is deleted its clock starts none (each fire time is skipped, saying why), while the user's clocks start the user's agents.

## Considered options

- **The schedule in a `clocks` table, with an item pointing at it**: rejected. Two records to keep in step, and copy, undo and zone moves would each need to carry the table row along.
- **Runs in the item's data**: rejected, for the undo and broadcast reasons above, and items' 64 KB cap.
- **A drawn edge from the clock as the join**: deferred. Flow edges join agents only, and a connector is a drawing. The clock's own data names its agent, the editor picks it, and a dashed tether shows it, as an agent note's does.
