# Agents learn the board from an `agent-board` CLI and a small stdio MCP, told once

The maintainer wants a Claude or Codex on the board to know about its zones, tiles, groups and edges, as cmux tells a session about its workspaces. His rule: tell the model **once** where it is and to read `agent-board --help`, and let it work out the rest. So the help text is the product, and nothing long is injected into the prompt.

## One API, two faces

- **Board ops** (`packages/daemon/src/board-ops.ts`) is the one module the CLI and the MCP call. It reads the board through the methods the app already uses (`zone.list`, `agent.list`, `shell.list`, `flowEdge.list`, `item.list`) and renders each view as text and as JSON. There is no parallel API.
- **Two new daemon methods**, only where something was missing: `board.identify { token }` (who holds a board token: the session, its tile, and the tile's zone now) and `board.setStatus { token, summary, progress? }` (that agent's own status).
- **The CLI**, `agent-board`, is the app's own executable run as Node (ADR-0001). `agent-board --help` teaches the concepts (zone, group, tile, agent, shell, edge, item), refs and commands. Commands: `identify`, `tree`, `zones`, `agents` (`ls`), `shells`, `edges`, `show <ref>`, `status set <summary> [--progress n]`, `mcp`, and `rpc <method> [json]` as an escape hatch, which in a session reaches only what the other commands do (below). Read commands take `--json`. The daemon's own commands (`daemon`, `stop`, `hook`) stay as they were.
- **The MCP server**, `agent-board mcp`, speaks stdio JSON-RPC by hand (no SDK dependency) with four tools: `whoami`, `board`, `connections` (the edges into and out of the caller, from its side), and `set_status`. ADR-0014 adds `ask` and `present_plan`, which wait on the user and so are MCP tools alone, with no CLI command; the server passes a client's `notifications/cancelled` on by closing that call's daemon connection. Its `instructions` are two sentences: you are on agent-board, and run `agent-board --help`. Each tool call connects afresh, so a daemon restarted meanwhile is found again.
- **Refs** are `<kind>:<start of id>`, at least four characters and as many more as tell it from the others of its kind (`zone:4f2a`, `agent:9c1e`), like git's short hashes. The ticket's example was numbers (`zone:3`), but every id is a UUID and nothing gives a stable number without a counter column per table; a position in a list would change meaning when something before it went, which would be wrong for a later `send agent:7`. A whole id works, a unique name works alone or after its kind, and `me` is the caller's tile. A name that more than one thing has is an error listing them by ref.

## Injection: every session the app starts

- **Env** (`board-env.ts`, added by the session host to every session it starts, agent or shell pane, fallback shells too): `AGENT_BOARD_SOCKET`, `AGENT_BOARD_SESSION_ID`, `AGENT_BOARD_ZONE_ID` (the zone as it started; only a hint, since tiles move: `identify` asks the daemon), `AGENT_BOARD_IDENTITY`, and the CLI's folder first on `PATH`. A login shell's profile can still reorder or reset `PATH`; Settings' install (below) covers that.
- **The CLI launcher.** The daemon (re)writes `agent-board` beside the Codex hook shim (`~/.agent-board/bin/agent-board`, ADR-0004) at start: `ELECTRON_RUN_AS_NODE=1 exec <app> <entry> "$@"`. It is the same app the daemon runs, follows the app when it moves or updates, and is what sessions find on `PATH`. The ticket said "the bundled CLI's directory"; a launcher the daemon writes works the same in dev, in tests and packaged, so nothing is added to the `.app` bundle. The hook shim and its trusted command string are unchanged.
- **MCP.** Claude gets `--mcp-config '{"mcpServers":{"agent-board":{"type":"stdio","command":"<launcher>","args":["mcp"]}}}'` next to its `--settings`; Claude starts the server with its own env. Codex gets `-c mcp_servers.agent-board.command=…`, `.args=["mcp"]` and `.env_vars=[the four board vars]`, since Codex passes an MCP server only a few env vars of its own. `env_vars` is per-server env forwarding as Codex's config documents it; a Codex too old to know the key would need upgrading. On by default; a zone's ⋯ menu turns it off for agents started in it afterwards (`zones.board_mcp`, `zone.configure { boardMcp }`). The CLI and env stay either way.
- **Not yet verified against a real Codex.** Codex runs the model's shell commands in its sandbox, and its default may deny connecting to the daemon's unix socket. The MCP server is started outside the sandbox, so it is unaffected. Codex's docs list `mcp_servers.<name>.env_vars`, but this hasn't been run against a real Codex. In a session, a CLI that can't reach the socket says to use the agent-board MCP tools instead. A one-off manual check with a real Codex (`agent-board identify` in its shell, and the `whoami` tool) should settle both points, and its result belongs here.
- **Install for other terminals.** Settings › Command line › Install command-line tool links `~/.local/bin/agent-board` to the launcher, VS Code-style: no sudo, and it replaces only a link, never a file of someone else's. Outside a session the CLI finds the daemon of `$AGENT_BOARD_DATA_DIR`, else the app's own data dir.

## Trust

- **The socket is still the user's (ADR-0002).** It is theirs alone (0700), and a connection that never presents a board token can call any method the app can: a person's `agent-board rpc`, or the app itself.
- **A board token narrows its connection to an allowlist.** Once a connection presents one (`board.identify`, or `board.setStatus`), the daemon refuses every method outside `BOARD_CALLER_METHODS` with `BOARD_ERROR.notAllowed`: the board's reads (`daemon.health` and the `zone`, `agent`, `shell`, `flowEdge`, `item` and `connector` lists) and `board.*`. Nothing that starts, types to, answers for or stops a session, or changes a setting; but for `board.handoff` (ADR-0012), which delivers to another agent only along the caller's own edges, as its turn's end already did. The guard (`guardBoardCallers`) wraps the daemon's whole method table, so it holds however the call arrives: a CLI command, its `rpc`, or the MCP server, all of which present the env's token before anything else. `agent-board rpc --help` lists the allowlist, and the main help says `rpc` in a session reaches only the reads and your own status.
- **It is a guard on what this feature hands the model, not a sandbox.** An agent runs as the user, so one that went out of its way could open the socket itself without presenting its token, as it could before this ticket. What the ticket rules out is the board CLI or MCP offering it: nothing they advertise can approve another agent's permission prompt, type into its terminal, or spawn, stop or delete agents.
- **Board token.** The token rides with each `board.*` call, so "only your own status" holds by construction; presenting it also narrows the connection, as above. It travels as `AGENT_BOARD_IDENTITY`: Codex keeps any var whose name has KEY, SECRET or TOKEN in it out of the model's shell by default (`shell_environment_policy.ignore_default_excludes = false`), so a name with "token" in it would never reach Codex's `agent-board`. Each session start mints a new random token; the daemon keeps only its SHA-256, in memory, mapped to the session while it is live. A token no live session holds is refused (`BOARD_ERROR.unknownToken`): the CLI and every MCP tool fail with that rather than fall back to anonymous reads. With no token at all (a person's terminal), reads work, `status set` is refused, and the orchestrator commands act as the user (ADR-0011).
- **The hook token stays hidden from Codex's model.** It can post hook events, which the board token can't. Codex's `shell_environment_policy.exclude` narrows from `AGENT_BOARD_*` to `AGENT_BOARD_HOOK_*`, so the board vars reach the model's shell and the hook URL and token don't. Claude's hook token is in Claude's own env, as before, because Claude interpolates it into its `http` hook header. Claude's own tools may see it there, and ADR-0004 already treats it as readable by the agent: it can forge events only for its own tile.
- **What agents can't do here.** Nothing in this ADR spawns, sends to, interrupts or closes another agent, or changes permissions, permission modes or settings. ADR-0011 adds `agent-board new|send|wait|read|interrupt|close` and their MCP tools for an agent the user lets orchestrate, widening the allowlist for it alone; permission modes and settings stay out of every agent's reach.
- **Decided by who is calling.** The guard asks the daemon who holds the token (`BoardCaller.side`), never the CLI. An agent's own session keeps the allowlist above, ended or not. Every other session the app starts (a shell tile, a tab, an ended agent's shell) is on the user's side, as is whatever the user runs in it by hand: it also reaches the orchestrator methods at board scope, and `agent.setOrchestrate` (`USER_SIDE_METHODS`). It still never types into a session, answers or decides a permission prompt, or changes another setting, so an agent started by hand in a board shell can't either. The governance review judged each check by whether it keeps a well-meaning or prompt-injected agent, following the help, away from an irreversible or permission-changing action; a check that only blocked the user's own hand went.

## Status

- An agent's **status** is one line, at most 200 characters (`MAX_STATUS_LENGTH`), and an optional progress 0 to 100, kept in `agents.status_summary`, `status_progress` and `status_updated_at`. Its tile shows it in place of the task (`· 40%` after it), with the task in the tooltip; until it sets one, the tile shows the task as before. A longer summary is refused with its length, so the agent learns the cap, rather than cut.
- **Last writer wins.** A new status replaces the old one. No previous value is kept. When the user can edit it by hand (not built here), a hand edit and an agent's update replace each other the same way: whoever writes last.

## Considered options

- **A long system prompt describing the board**: rejected by the maintainer's "tell it once" rule. It costs tokens every turn and goes stale.
- **The MCP SDK**: rejected for now. Four tools over newline JSON-RPC is a page of code, and the fake harnesses need to speak the same wire without the SDK.
- **Numeric refs from a counter column per table**: rejected for now as a schema change for every table to save a few characters. Prefix refs need nothing stored.
- **An unrestricted `rpc` in sessions** (the first round of this ADR): rejected in review. The help an agent is told to read would have advertised approving a sibling's permission prompt or typing into its terminal, against the ticket's Trust section.
- **Refusing `rpc` outright in a session**: rejected. The allowlist keeps it useful for reads the commands don't format, and the guard sits in the daemon, where the MCP server and any other client meet it too.
