# Agents learn the board from an `agent-board` CLI and a small MCP, told once

The maintainer wants a Claude or Codex on the board to know about its zones, tiles, groups and edges, as a terminal multiplexer tells a session about its workspaces. His rule: tell the model **once** where it is and to read `agent-board --help`, and let it work out the rest. So the help text is the product, and nothing long is injected into the prompt.

## One API, two faces

- **Board ops** (`packages/daemon/src/board-ops.ts`) is the one module the CLI and the MCP call. It reads the board through the methods the app already uses (`zone.list`, `agent.refreshBranches` and `agent.list`, `shell.list`, `flowEdge.list`, `item.list`) and renders each view as text and as JSON. There is no parallel API.
- **Two new daemon methods**, only where something was missing: `board.identify { token }` (who holds a board token: the session, its tile, and the tile's zone now) and `board.setStatus { token, summary, progress? }` (that agent's own status).
- **The CLI**, `agent-board`, is the app's own executable run as Node (ADR-0001). `agent-board --help` teaches the concepts (zone, group, tile, agent, shell, edge, item), refs and commands. Commands: `identify`, `tree`, `zones`, `agents` (`ls`), `shells`, `edges`, `show <ref>`, `usage` (ADR-0025), `status set <summary> [--progress n]`, `mcp`, and `rpc <method> [json]` as an escape hatch, which in a session reaches only what the other commands do (below). Read commands take `--json`. The daemon's own commands (`daemon`, `stop`, `hook`) stay as they were.
- **The MCP server**, `agent-board mcp`, speaks stdio JSON-RPC by hand (no SDK dependency) with four tools: `whoami`, `board`, `connections` (the edges into and out of the caller, from its side), and `set_status`. ADR-0025 adds `usage`, the plan usage reading. ADR-0014 adds `ask` and `present_plan`, which wait on the user and so are MCP tools alone, with no CLI command; the server passes a client's `notifications/cancelled` on by closing that call's daemon connection. Its `instructions` are a few short sentences: you are on agent-board; run `agent-board --help`; a turn ending tells no one, so call `needs_you`; list and read the memories before you start (`memory_read` with no memory only lists them), and add to one before you finish or hand off; something only the user can do, later, goes on their to-do list with `remind`. An orchestrator's add one more: take the next item from its zone's queue when its crew has room. Each tool call connects afresh, so a daemon restarted meanwhile is found again.
- **Two transports, one server**. The handlers (`boardMcpHandlers`) are written once and served two ways: over stdio by `agent-board mcp`, for Codex agents and clients outside the app, and over Streamable HTTP by the daemon, at `POST /mcp` on the hook listener (`board-mcp-http.ts`), which is what Claude agents use. A stdio server is a process per client, and each was a Node runtime of its own (about 55 MB, half the app's memory with a dozen agents) only to relay calls to the daemon's socket; over HTTP no agent starts anything. Measured with 10 fake Claude agents each holding an `ask` open: 10 `agent-board mcp` processes using 788 MB before, none after, and the daemon's own growth within noise. The HTTP side is stateless (no `Mcp-Session-Id`, no GET stream): one JSON-RPC message per POST, a notification answered 202, a request with its JSON, and a tool call with an event stream whose headers go at once and a comment line every 15 s, since `ask`, `present_plan` and `wait` hold a call for minutes and a client gives up on one that says nothing for long (Claude's HTTP idle window is five minutes). A call ends when its client hangs up or posts `notifications/cancelled`; either closes its daemon connection, as on stdio. A plan's relative `path` is read from where the session started, not the daemon's folder.
- **Steps cards** (ADR-0014). `agent-board steps new|ls|read|done|wait|add|answer|close`, as the MCP tools `steps_new`, `steps_read` (a card, or the list) and `steps_update` (the rest), over three board-caller methods: `board.newSteps`, `board.readSteps` and `board.updateSteps`. `steps done` takes `tick` too. The user's own methods (`steps.answer`, `steps.tick`, `steps.send`) are not in the allowlist, as `ask.answer` isn't: an agent answers a set only as the orchestrator it was put to. An agent reads the cards in its zone, loose ones, and any it made, answers or is named on; it ticks only a to-do that names it, and adds to or closes only a card it made. `item.list` leaves out the steps cards outside an agent's scope, for its own session's connection, so a ref to one it can't read doesn't resolve either; the user's side lists them all. The scope rule (`item-scope.ts`) is one function, for any kind read this way.
- **Memories and queues** (ADR-0005). `agent-board memory ls|read|add|edit|rm|history|restore|new` and `agent-board queue ls|read|add|take|drop|done|edit|rm|history|restore|new`, as the MCP tools `memory_new`, `memory_read` (the list, a memory, an entry, or its history) and `memory_update` (the rest), and the same three for queues, over the board-caller methods `board.newMemory|listMemories|readMemory|changeMemory|memoryHistory` and their queue twins. The user's own (`memory.read|change|history`, `queue.read|change|history`) are not in the allowlist. A memory or queue is named by its ref or its title, an entry by its key or the start of its id, a job by the start of its id. Their scope is `item-scope.ts`'s rule, the steps cards' own, with No agents on top; `item.list` leaves out those outside an agent's scope for its own connection. Anyone in scope may change any entry, the user's too, since history takes a change back; a job another agent holds is only its taker's, or the user's, to change. A take is a lease on the taker's session: as the session ends (but not for a restart or hibernation), its jobs go back to the front of their queues, each drop counted, and a job always goes back, never parked. An agent that kept its jobs through a pause or a restart and is then deleted has no exit to come, so its deletion (`agent.removed`, by any path) puts them back too, and so does the daemon's start for any taker no longer on the board. Nothing in either is typed at any agent. Agents learn of them from the MCP instructions above, which name the moment to use each (Claude defers the board's tools, so an agent sees a tool's description only once it has chosen the tool), from the app's own role templates, which say the same, and from `agent-board --help`. Every answer names the memory or queue it came from and leads to the next step: an empty list says how to make one, an empty memory how to add the first entry, and a finished job how many wait and which is next. A queue row has a kind, by who the queue is for (ADR-0005): `--kind` (`kind` to the MCP) picks it, and no kind means the queue's default (a task, or backlog on the user's queue). The old `job` and `note` still work, as the default and info. One job can be given as a headline of at most 80 characters and a body (`--body`; the MCP's `headline` and `body`), and `done` takes a `--result` (`result` to the MCP) saying what was done. A headline given with `--body` still takes a link after ` -> `. Putting a row off for later and skipping it are the user's alone (`queue.change`'s `later` and `skip`), on their own queue; neither makes a version, and a row put off is shown again before it is skipped. The kinds `add` takes are one list, `QUEUE_ADD_KINDS`, which the CLI, the MCP schema and the daemon share. A memory holds **facts** (a key's value, or a note) and **documents** (text kept whole under a title, from `memory add --doc <title>`, `memory_update`'s `document`, or a file with `--file`). A read of a memory gives its facts in full and its documents by title, size and line count alone, so a long one costs nothing until an agent names it; an entry read by name comes back whole. The daemon leaves a document's text out of an agent's listing itself (`MemoryEntry.listed` holds its size), so `--json` gets no more than the text does; the user's `memory.read` has every text. The daemon counts the agents whose read returned an entry whole, and an answer says how many and who last did (`read by 2 agents, last Impl …`), so an agent can tell what others have relied on. An entry untouched for 30 days reads as **stale**, and the answer says to `memory confirm` one still true (today's date on it, and a `confirm` row in its history with no value: a run of them is one row, and none counts toward a row's versions or the history's bytes, so confirming never pushes an edit out) or to edit or remove it.
- **To-do lists.** `agent-board remind <text>…|ls [--mine]|done|undo|rm <n>`, as the MCP tools `remind`, `remind_read` and `remind_update`, over the board-caller methods `board.remind`, `board.readTodos` and `board.changeTodo`. The user's own `todo.change` is not in the allowlist. Each agent has one list, made under its tile by its first `remind` and found again by its owner; a line is named by its place in the caller's own list. An agent reads the lists in its scope (`item-scope.ts`'s rule, with its own list always), and ticks, unticks or takes off only a line it wrote on its own list: a line the user wrote is the user's. A tick is saved with who and when, and nothing is typed at any agent: an agent that wants to know reads its list. The MCP instructions say so (above).
- **Crew cards** (ADR-0011). A running crew's card is a board item of kind `crew` with no board-caller method of its own: an agent reads its crew with `agent-board crew`. `item.list` leaves out the crew cards outside an agent's scope for its own connection, by `item-scope.ts`'s rule: it lists those in its zone, loose ones, and its own crew's (as its builder, one of its reviewers, or the orchestrator that started it). A connection whose session the board no longer knows (its agent was deleted under it) has no one to read as, so it lists nothing kept to a scope: no crew card, steps card, memory or queue.
- **Item events keep the same scope.** The daemon sends `item.updated` and `item.removed` for a crew card, steps card, memory or queue to a connection only if its `item.list` would list the item: the one visible rule, applied to each event per connection, and to a removed item as it was just before it went. An agent that holds a connection open (a `wait`, the MCP) hears nothing of those outside its scope, and one whose session the board no longer knows hears none of them. Other kinds of item, and every item to the app's connection or a session acting for the user, are sent as before. An item that moves out of an agent's scope stops reaching it with no event to say so; its next `item.list` leaves it out. Scoping starts once a connection presents a board token, and a client that never presents one is the user's: this keeps one agent from reading another's items through the board, and is not a boundary against a client that would leave its token unpresented.
- **Refs** are `<kind>:<start of id>`, at least four characters and as many more as tell it from the others of its kind (`zone:4f2a`, `agent:9c1e`), like git's short hashes. The ticket's example was numbers (`zone:3`), but every id is a UUID and nothing gives a stable number without a counter column per table; a position in a list would change meaning when something before it went, which would be wrong for a later `send agent:7`. A whole id works, a unique name works alone or after its kind, and `me` is the caller's tile. A name that more than one thing has is an error listing them by ref.

## Injection: every session the app starts

- **Env** (`board-env.ts`, added by the session host to every session it starts, agent or shell pane, fallback shells too): `AGENT_BOARD_SOCKET`, `AGENT_BOARD_SESSION_ID`, `AGENT_BOARD_ZONE_ID` (the zone as it started; only a hint, since tiles move: `identify` asks the daemon), `AGENT_BOARD_IDENTITY`, and the CLI's folder first on `PATH`. A login shell's profile can still reorder or reset `PATH`; Settings' install (below) covers that.
- **The CLI launcher.** The daemon (re)writes `agent-board` beside the Codex hook shim (`~/.agent-board/bin/agent-board`, ADR-0004) at start: `ELECTRON_RUN_AS_NODE=1 exec <app> <entry> "$@"`. It is the same app the daemon runs, follows the app when it moves or updates, and is what sessions find on `PATH`. The ticket said "the bundled CLI's directory"; a launcher the daemon writes works the same in dev, in tests and packaged, so nothing is added to the `.app` bundle. The hook shim and its trusted command string are unchanged.
- **MCP.** Claude gets `--mcp-config '{"mcpServers":{"agent-board":{"type":"http","url":"http://127.0.0.1:<port>/mcp","headers":{"Authorization":"Bearer ${AGENT_BOARD_IDENTITY}"}}}}'` next to its `--settings`; Claude fills the token in from its own env, so it is in no process's argv. Codex keeps the stdio server: `-c mcp_servers.agent-board.command=<launcher>`, `.args=["mcp"]` and `.env_vars=[the four board vars]`, since Codex passes an MCP server only a few env vars of its own. Its HTTP config (`.url` and `.bearer_token_env_var="AGENT_BOARD_IDENTITY"`) is what Codex documents and parses, but no real Codex has been seen calling it, and a Codex agent with a broken board MCP would lose `ask`, `present_plan` and handoffs. So it moves to HTTP once a real Codex has called `whoami` there; most agents are Claude's, which is where the memory goes. The board MCP is still given only with the CLI launcher, which its instructions send the model to. On by default; a zone's ⋯ menu turns it off for agents started in it afterwards (`zones.board_mcp`, `zone.configure { boardMcp }`). The CLI and env stay either way.
- **Checked against the real CLIs, without a model turn**. Claude Code 2.1.301, started with the config above against the daemon's `/mcp`, filled `${AGENT_BOARD_IDENTITY}` into the header (the docs name only `.mcp.json` for that), probed `server/discover` (a revision the server doesn't speak: it answers method-not-found, and Claude falls back), then sent `initialize`, `notifications/initialized` and `tools/list`. Codex 0.162 takes the HTTP overrides as a `streamable_http` server with that bearer env var (`codex mcp get`), but no real Codex has made a call to it yet, which is why Codex stays on stdio.
- **Not yet verified against a real Codex.** Codex runs the model's shell commands in its sandbox, and its default may deny connecting to the daemon's unix socket. The MCP client is Codex's own process, outside the sandbox, so it is unaffected. In a session, a CLI that can't reach the socket says to use the agent-board MCP tools instead. A one-off manual check with a real Codex (`agent-board identify` in its shell, and the `whoami` tool) should settle both points, and its result belongs here.
- **Install for other terminals.** Settings › Advanced › Command line › Install command-line tool links `~/.local/bin/agent-board` to the launcher, VS Code-style: no sudo, and it replaces only a link, never a file of someone else's. Outside a session the CLI finds the daemon of `$AGENT_BOARD_DATA_DIR`, else the app's own data dir.

## Trust

- **The socket is still the user's (ADR-0002).** It is theirs alone (0700), and a connection that never presents a board token can call any method the app can: a person's `agent-board rpc`, or the app itself.
- **A board token narrows its connection to an allowlist.** Once a connection presents one (`board.identify`, or `board.setStatus`), the daemon refuses every method outside `BOARD_CALLER_METHODS` with `BOARD_ERROR.notAllowed`: the board's reads (`daemon.health` and the `zone`, `agent`, `shell`, `flowEdge`, `item` and `connector` lists) and `board.*`. Nothing that starts, types to, answers for or stops a session, or changes a setting; but for `board.handoff` (ADR-0012), which delivers to another agent only along the caller's own edges, as its turn's end already did. The guard (`guardBoardCallers`) wraps the daemon's whole method table, so it holds however the call arrives: a CLI command, its `rpc`, or the MCP server, all of which present the env's token before anything else. `agent-board rpc --help` lists the allowlist, and the main help says `rpc` in a session reaches only the reads and your own status.
- **The HTTP MCP is the same caller as the stdio one**. The hook listener is bound to 127.0.0.1. A POST to `/mcp` must carry a live session's **board token** as `Authorization: Bearer`; without one, or with one no live session holds, it is refused 401 before its body is read, and one from a web page (an `Origin` that isn't this machine's) 403, against DNS rebinding. Each call then opens a connection to the daemon's own socket and presents that token, exactly as `agent-board mcp` in that session would, so `board.identify`, the allowlist guard, the checks on whom it acts on and the activity log hold unchanged, and one session's token acts only as that session. The ticket named the hook token; the board token is used instead because the daemon keeps only hashes, so a hook token would give the session's id but no board token to present, and acting as a session by id would be a second way in that skips the guard. The board token is also the weaker one: it can't post hook events.
- **It is a guard on what this feature hands the model, not a sandbox.** An agent runs as the user, so one that went out of its way could open the socket itself without presenting its token, as it could before this ticket. What the ticket rules out is the board CLI or MCP offering it: nothing they advertise can approve another agent's permission prompt, type into its terminal, or spawn, stop or delete agents.
- **Board token.** The token rides with each `board.*` call, so "only your own status" holds by construction; presenting it also narrows the connection, as above. It travels as `AGENT_BOARD_IDENTITY`: Codex keeps any var whose name has KEY, SECRET or TOKEN in it out of the model's shell by default (`shell_environment_policy.ignore_default_excludes = false`), so a name with "token" in it would never reach Codex's `agent-board`. Each session start mints a new random token; the daemon keeps only its SHA-256, in memory, mapped to the session while it is live. A token no live session holds is refused (`BOARD_ERROR.unknownToken`): the CLI and every MCP tool fail with that rather than fall back to anonymous reads. With no token at all (a person's terminal), reads work, `status set` is refused, and the orchestrator commands act as the user (ADR-0011).
- **The hook token stays hidden from Codex's model.** It can post hook events, which the board token can't. Codex's `shell_environment_policy.exclude` narrows from `AGENT_BOARD_*` to `AGENT_BOARD_HOOK_*`, so the board vars reach the model's shell and the hook URL and token don't. Claude's hook token is in Claude's own env, as before, because Claude interpolates it into its `http` hook header. Claude's own tools may see it there, and ADR-0004 already treats it as readable by the agent: it can forge events only for its own tile.
- **What agents can't do here.** Nothing in this ADR spawns, sends to, interrupts or closes another agent, or changes permissions, permission modes or settings. ADR-0011 adds `agent-board new|send|wait|read|interrupt|close` and their MCP tools for an agent the user lets orchestrate, widening the allowlist for it alone, and any agent's `send` back to an agent that messaged it (ADR-0011's reply path); permission modes and settings stay out of every agent's reach.
- **Decided by who is calling.** The guard asks the daemon who holds the token (`BoardCaller.side`), never the CLI. An agent's own session keeps the allowlist above, ended or not. Every other session the app starts (a shell tile, a tab, an ended agent's shell) is on the user's side, as is whatever the user runs in it by hand: it also reaches the orchestrator methods on any agent (`USER_SIDE_METHODS`). It still never types into a session, answers or decides a permission prompt, or changes another setting, so an agent started by hand in a board shell can't either. The governance review judged each check by whether it keeps a well-meaning or prompt-injected agent, following the help, away from an irreversible or permission-changing action; a check that only blocked the user's own hand went.

## Status

- An agent's **status** is one line, at most 200 characters (`MAX_STATUS_LENGTH`), and an optional progress 0 to 100, kept in `agents.status_summary`, `status_progress` and `status_updated_at`. Its tile shows it in place of the task (`· 40%` after it), with the task in the tooltip; until it sets one, the tile shows the task as before. A longer summary is refused with its length, so the agent learns the cap, rather than cut.
- An agent's **work category** rides on the same call: `status set --category <one of seven, or none> [--label <words>] [--on "who · ref"]`, and the MCP's `set_status` with `category`, `label` and `waiting_on { who, ref }`. It is kept in `agents.work_category` and the columns beside it, and a set replaces the whole of it (ADR-0024). `identify` says the agent's category, or what the board guesses and why; `show` adds a category row while one is set.
- An agent's **purpose**, what it is for, rides on it too: `status set --description <text>` and `set_status` with `description`, at most 80 characters, `''` to clear it. It is kept in `agents.purpose` until it is set again; an orchestrator sets it for its crew as it does the status line. `new --description <text>` (and `new --prefab`, and `new_agent`'s `description`) sets it as the agent starts, in one line and cut to the cap rather than refused. The ⌘K switcher shows and finds agents by it, and the tile's hover card leads with it.
- **Last writer wins.** A new status replaces the old one. No previous value is kept. When the user can edit it by hand (not built here), a hand edit and an agent's update replace each other the same way: whoever writes last.

## Records

An agent's sidebar (its session window's details) is written by the agent, not worked out for it.

- **The store.** `agent_records (session_id, kind, key, data, recorded_at, deleted_at)`, one row per entry, keyed by kind and key: `pr` by `owner/repo#n` in lower case (any URL or spelling of the same pull request is one entry, as GitHub's names are the same in any case), `doc` by its real path through any link, `crew` by the started agent's session, `pin` as below. Every `Agent` carries its rows as `records`, so a record reaches the sidebar with the `agent.updated` it causes, within a second.
- **Writing.** `board.record { token, kind, url|path, title?, forOrchestrator? }`, in the board-caller allowlist like `board.setStatus`, and only ever on the caller's own sidebar, or for a doc with `forOrchestrator`, on the sidebar of the orchestrator that started it (`spawnedBy`), saying who wrote it. The CLI is `agent-board record pr <url> [--title t]` and `record doc <path> [--for orchestrator]`; the MCP tools are `record_pr` and `record_doc`. A doc must be a file when it is recorded; one recorded for the orchestrator goes on the agent's own sidebar too. The daemon also records what it sees an agent do itself: the pull request `open-pr` opens, the handover file a hand-off carries, and each agent an orchestrator starts (with existing crews backfilled by the migration).
- **A recorded pull request is looked up.** One on a branch the agent's own lookups don't reach is asked about by its number (`gh pr view`, at most ten per agent each round, and at once when recorded), so its row has its title, state and checks like any other (`Agent.recordedPullRequests`). One last seen merged or closed is not asked about again until it is recorded again. One gh can't read keeps what was last seen of it, logged once, and never stops the agent's own pull requests being read. Recording one again with no title keeps the title it had.
- **Records win; guesses fill the gaps**, in every section: gh's pull requests (its own branch's, else those it pushed to), hooks' subagents, the agents whose `spawnedBy` it is, and its worktree's `.agent-board/handover.md` (`Agent.guessedDoc`). A guess whose key a record has is drawn as that record.
- **Deleting.** The user may delete a record (`agent.setRecordDeleted`, the user's alone), never edit one. The row stays with `deleted_at`, so the same entry's guess stays hidden too, rather than coming straight back as "guessed" and making Delete look broken; recording it again clears `deleted_at`. Undo and the section's "Show" clear it as well.
- **Reading a doc.** `agent.readDoc { sessionId, path }` (the user's alone) reads only a path recorded on that agent (a hand-off doc, or a pinned file) and not deleted, or its guessed handover, at most 1 MB, and never one made a link since it was recorded; the session window shows it read-only in a Doc tab, its Markdown rendered and its HTML drawn as an HTML plan's page is (ADR-0014).
- **Pins.** A `pin` record is what an agent wants the user to see: `board.record { token, kind: 'pin', path|url|note, label?, forOrchestrator? }`, exactly one of a file (kept by its real path, as a doc), a link a web tab opens (`isWebTabUrl`: https, or http on this machine, never with a name or password; at most 2,048 characters), or a note of at most 2,000 characters, which needs a label. A label's runs of whitespace are one space. The key is the path, the link, or `note:` and the label, so a note pinned again under the same label replaces its text. No migration: a kind is a value of `agent_records.kind`, and a daemon that doesn't know one leaves its rows alone. With `forOrchestrator` it goes on the orchestrator's sidebar alone, unlike a doc, as the agent pinned it for that orchestrator's user, keyed under its own session (`from:<session>:<key>`): a crew member's pin never replaces the orchestrator's own or another crew member's, and its unpin finds only its own there. `board.unpin { token, path|url|label, forOrchestrator? }` deletes the row outright rather than setting `deleted_at`: a withdrawn pin is no record the user deleted, so the section's "Show" must not bring it back. The CLI is `agent-board pin <path|url> [--label]`, `pin --note <text> --label <label>` and `unpin <path|url> | --label <label>`; the MCP tools are `pin` and `unpin`. A pinned Markdown or HTML file opens in a Doc tab, any other file is revealed in Finder (`session:revealFile`, which only selects it, never opens it), a link opens in a web tab, and a note shows its text on the sidebar.
- **The page.** An agent's page (`Agent.page`), the shelf its sidebar opens on, is written whole with `board.setPage { token, page }`, in the board-caller allowlist, on the caller's own sidebar alone: no `forOrchestrator`, as the page is its own say about its own work. `page` null clears it, and is refused when there is none, as `unpin` refuses a pin that isn't there. It is the agent's **name** (at most 12 characters) and **icon**, and 1 to 12 **blocks**, each `{ kind, title?, icon?, tone? }` and by kind: `heading` (a title, a line or two, progress 0-100), `figures` (one or two of value and label, each with its own icon and tone), `checklist` (items of text and a state: todo, doing or done, with at most one doing, drawn as the current item), `callout` (text), `links` (each a URL a web tab opens or a file, checked as a pin's are, with a label) and `note` (a title and text). Icons are from a curated set of about 40 (`PAGE_ICONS`), which leaves out every mark the board draws with a fixed meaning (a pull request, a branch, the crew, the workspace, a pin, the robot, a flag, a link's, a note's or a file's row, documents, interrupting, timers, Ask Claude's sparkles, the shelves' stack), and tones are neutral, blue, green, violet or teal (`PAGE_TONES`), so an agent can never draw in the board's orange or red. The daemon checks every field, refuses one a block doesn't take, counts characters as graphemes after NFC, takes out control characters (bar a line break and a tab) and bidi controls, and names the block and field it refuses; a refused page leaves the old one. A link's relative path is from the caller's working directory: the CLI and the tool send it absolute. A stored page is read back through the same checks, minus the file's: a later daemon's icon becomes none (the tab's a default), its tone neutral, and a block of a kind or shape this daemon doesn't know is left out, so a window only ever gets blocks it can draw; a page with none left is no page. Blocks, never Markdown or HTML: the board draws every block in its own design. It is kept as one row of `agent_records` of kind `page`, with no migration, but is no record: `Agent.records` leaves it out, and the user's delete never reaches it. A file a page links to is one `agent.readDoc` reads. The CLI is `agent-board page --file <path|-> [--name] [--icon]` (the page as JSON, or its blocks alone) and `page --clear`; the MCP tool is `set_page`, whose schema offers the icons and tones as its choices.
- **Documents are listed, not recorded.** The sidebar's Documents section lists `Agent.docs` (ADR-0018) and its latest plan as they are, each opening its tab. They are the daemon's rows of what the agent showed, not entries it wrote about its work, so there is nothing to guess and nothing for the user to delete there.

## Considered options

- **A long system prompt describing the board**: rejected by the maintainer's "tell it once" rule. It costs tokens every turn and goes stale.
- **The MCP SDK**: rejected for now. Four tools over newline JSON-RPC is a page of code, and the fake harnesses need to speak the same wire without the SDK.
- **Numeric refs from a counter column per table**: rejected for now as a schema change for every table to save a few characters. Prefix refs need nothing stored.
- **An unrestricted `rpc` in sessions** (the first round of this ADR): rejected in review. The help an agent is told to read would have advertised approving a sibling's permission prompt or typing into its terminal, against the ticket's Trust section.
- **The hook token as the HTTP MCP's bearer** (the ticket's first wording): rejected, as under Trust: it would need the daemon to act as a session without its board token.
- **Calling the method table in-process from `/mcp`** instead of over the daemon's own socket: rejected. The guard wraps the socket's connections, and a shortcut beside it would have to copy it.
- **HTTP for Codex too, now**: deferred. Codex documents and parses `url` and `bearer_token_env_var`, but until a real Codex has made a call, Codex agents keep the stdio server they were known to work with.
- **Refusing `rpc` outright in a session**: rejected. The allowlist keeps it useful for reads the commands don't format, and the guard sits in the daemon, where the MCP server and any other client meet it too.
