# App shell: Electron + TypeScript

We build the desktop app on Electron with TypeScript end to end (React renderer, Node main process and daemon), because `node-pty` + `xterm.js` are the proven PTY/terminal pair (VS Code), Chromium renders identically on every OS, and a single language lets one test harness (Vitest + Playwright's Electron driver) cover unit and end-to-end. We accept heavier RAM and bundle size.

## Considered options

- **Tauri v2 (Rust)** — small and fast, `portable-pty` works, but WebKit on macOS/Linux renders and performs differently from Chromium (xterm.js WebGL, canvas pan/zoom), and a second language splits the codebase and test harness.
- **Wails (Go)** — matches the maintainer's main language and `creack/pty` is solid, but Wails v3 is still pre-stable, the ecosystem is small, and it carries the same webview caveats as Tauri.

## Consequences

- Native modules (`node-pty`) must be rebuilt for Electron's ABI; the daemon runs on Electron's bundled Node (`ELECTRON_RUN_AS_NODE`) so one build serves both. SQLite uses the built-in `node:sqlite`, so it needs no rebuild (ADR-0005).
- E2E tests drive the real packaged app through Playwright's `_electron` API. Until packaging lands, they launch the built main bundle (`apps/desktop/out/main/index.js`) with the Electron binary; switch to the packaged executable in the packaging ticket.

## Amendments

**Update**:

- **Packaging.** `pnpm package` builds an unsigned, unpacked (no asar) macOS `.app` with electron-builder `--dir`. node-pty's N-API prebuilds load in Electron as they are, so the package skips the native rebuild (`npmRebuild: false`). Once the build has succeeded, `pnpm package` also installs the app as `~/Applications/agent-board.app`: it quits a running app, copies the new one beside the old and swaps them, so a failed build or copy leaves the working app in place, and offers to reopen the app. `pnpm package --no-install` builds only; installing is macOS only. It installs by default.
- **E2E tests stay on the built main bundle.** The suite still launches `apps/desktop/out/main/index.js`, so the dev loop needs no packaging step. Packaging takes about 10 s and a 320 MB copy. One more test, `e2e/packaged.spec.ts` (`pnpm test:e2e:packaged`, run in CI after `pnpm package`), launches the packaged executable. It checks that the app starts its own daemon from the package and that node-pty runs a shell session there. This replaces the plan above to switch the whole suite to the packaged executable.

**Update**: every window stays on the app. It opens no other window (`setWindowOpenHandler` denies all)
and navigates nowhere but the app's own page (`will-navigate`). An https link either would have opened goes to the OS
browser through the same https-only path as tracker links; anything else is dropped. Note text and tracker data come
from outside the app, so nothing they hold may load in an app window.

**Update**: the window chrome (`main/chrome.ts`).

- **macOS has no title bar** (`titleBarStyle: 'hiddenInset'`). The traffic lights float over the page: on the board, centred on the top islands' midline, left of the board-menu island (the maintainer's pick U2); in a popped-out session window, inline at the start of its header (W). The renderer knows the chrome from `window.agentBoard.windows.chrome` and sets `html[data-chrome='inset']`, which leaves room for the lights.
- **Window dragging** is limited to a thin strip along the top of the board, the traffic lights' corner (not while a session window is shown on the board, which then sits below the lights' row) and the board menu's empty space; in a popped-out window, its header's empty space (`-webkit-app-region: drag`, with every control `no-drag`). The board needs every other pointer event. macOS handles a double-click on a drag region (zoom, by the user's setting).
- **Full screen** hides the traffic lights: main tells the renderer (`window:fullScreen`), which sets `html[data-full-screen='true']` (`'false'` otherwise), and the island or header moves into the room they leave.
- **Windows and Linux keep the native frame**, with its window controls. `titleBarOverlay` was not needed for chrome C, whose islands float below a native title bar just as well.

**Update**: slice 4, tabs drag between OS windows (`main/tab-drags.ts`). It replaces an earlier, held slice, which was built on the one-strip model.

- **The drag is the platform's own HTML5 drag**, as inside one window. Main-process pointer tracking with window hit-testing was the other way; it would have meant a second drag model beside the in-window one, with its own ghost, slot and overlays.
- **Every window hears what is dragged, and goes by that.** The window a drag starts in tells main (`tabDrag:set`), which tells every window. Drop targets (a strip's slot, a pane's overlay, the board) take a drag because one is on, not because its data type (`application/x-agent-board-shell`) reached them, so they don't depend on Chromium carrying a custom type to a window the drag didn't start in. The window that takes the drop ends the drag everywhere, as the tab it came from may go with the move; if the window it began in closes first (a tab window losing its last tab), main ends it.
- **The board's window makes every move**, and its one undo history has them all. A pop-out asks it through main (`tabDrag:move`) and sends it ⌘Z and ⇧⌘Z (`tabDrag:history`) while its keyboard is in no field or terminal (Ctrl+Z off macOS, which a terminal keeps). Until the board says it is listening (`tabDrag:ready`) main keeps what is for it, opening its window if it is closed, so a drag is never lost; a pop-out's ⌘Z then has nothing to undo, and says so. A move the daemon refuses is reported in the board's window. After a move, every window takes its keyboard out of its terminal, so the next ⌘Z reaches the history.
- **Only the windows a move concerns may ask for it.** Main knows which window is the board's and whose window each pop-out is. Only the board's window may say it listens (`tabDrag:ready`: another saying so would leave every move waiting for nothing). A pop-out may ask for a move only into its own window, or, for a pull request, web or session tab, out of it; may end untaken only a drag from itself; and only the board or a tab's own window may hand its web page off. Nothing else moves another window's tabs.
- **Let go outside every window, a tab pops out.** A drag no window took (`dropEffect` none) tells main where its end says it was let go, else main reads where the pointer is (`screen.getCursorScreenPoint()`), as Chromium doesn't always give the end a place; under Wayland the pointer reads 0,0 there, so a drag whose end gives no place pops out in the screen's corner. Outside every visible window (a minimised one, or one full screen in another Space, doesn't count), the board pops it out there, its strip under the pointer, on that display. Escape over the desktop looks the same as a drop there, and pops out too.
- **Tabs that are only a place in a window** (a pull request, a web page, another session) move between windows in the daemon (`shell.moveSurface`), both layouts in one transaction in both windows' turns, which every window hears (`window.layout`) and takes as it is. A window's own writes (`shell.setWindowLayout`) carry the layout they were made from, and the daemon keeps one only over that one, so a write made before a tab moved in or out can't put it back or take it away again; the window takes the moved layout from the event instead, and never commits a layout drawn from before it; shells still move by their owner (`shell.moveTab`, `shell.movePane`). A pull request or web tab popped out on its own goes into a **tab window**, a pop-out that is no session's: its layout is kept as owner kind `tabs` (migration 0040), it holds no shell, and closes with its last tab. Closed by the user (not by the app quitting, after which it opens again with its tabs), it forgets its layout only as it last showed it (`shell.forgetWindow` compares), so a tab redone into it as it closes is kept; and the board, as it starts, pops out again any tab window kept that it has lost track of (`shell.tabWindows`), such as one whose pop-out the app quit before saving.
- **A web tab's page moves with it.** Before a move, or a whole window popping out or back in, its page is handed off (`web-tab:handOff`): it waits hidden, kept from its window's going, and the window that opens the tab next takes the page as it is, with no reload. One no window takes in 30 s (the window it went to isn't open) goes, but keeps its partition: the tab is still in that window's layout, and loads afresh there, signed in as it was, when the window opens. A move that fails hands it back.
- **E2e** play a drag between two windows as the platform would deliver it, to the app's own handlers (`dragstart` in one window, `dragover` and `drop` in the other, `dragend` back in the first), since offscreen windows have no pointer that crosses them; they set the pointer main reads. Chromium delivering a drag's `dragover` and `drop` to a second window at all is the one thing they can't show: it is checked by hand in the headed app.
