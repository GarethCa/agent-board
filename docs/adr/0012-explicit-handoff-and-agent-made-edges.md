# An agent hands off explicitly along its own edges, and orchestrators wire edges in their scope

Until now an agent could only read its edges (`connections`, ADR-0010); a hand-off was inferred from its turn ending (`Stop` with `last_assistant_message`). This lets an agent hand off when its work is ready, with what it chooses, and lets an orchestrator (ADR-0011) join agents with edges. The risk is reach: a hand-off types into another agent, and an edge decides who types into whom.

## Explicit hand-off: `board.handoff`

- **Any agent, along its own edges only.** `board.handoff { token, to?, message?, handoverPath?, json? }` is in `BOARD_CALLER_METHODS`: every agent may hand off, orchestrator or not. It acts on the edges whose `from` is the token's agent: with `to`, the edge to that agent alone. No edge at all, with no `to`, hands nothing on and resolves with no outcomes: it used to be `invalidParams`, but handing off is now also how an agent says its work is **finished** (`Agent.workFinishedAt`, below), which an orchestrator's worker with no edges must be able to say. The token must be the agent's own live session: a shell tile, a tab in its window, or an ended agent's shell is refused, as for orchestrating.
- **Naming an agent with no edge: a one-off edge (G28).** With `to` an agent it has no edge to, the hand-off makes one: manual, marked as made by the agent (`madeBy`) and as a one-off (`FlowEdge.oneOff`, `flow_edges.one_off`, migration 0045), carrying what it was given (a message, else a handover file, else JSON), and delivers along it at once. So it is drawn afterwards, as any agent-made edge is, its tooltip and Edge rules saying "A one-off hand-off from the agent", with the delivery in its history and the payload in **Last hand-off**. Named again, it goes along that edge, with what it is given then; the user's Send on it replays what it last carried (`flow_edges.one_off_text`, kept across a restart, since a message or JSON handed inline is no file to read again). It never starts an ended agent again: the user's Stop sticks against every peer, and only the user's Send along it, or an edge the user drew, relaunches one. That is what stops two agents relaunching each other for ever; one-off edges stay out of the auto-loop check, so a reply by name (a reviewer naming its implementer back) is never refused, and the user may still draw the edge back. The target must be in the agent's scope (`checkHandoffTarget`): its zone, or its orchestrator scope if the user gave it a wider one, or an agent it started; never itself, and never an orchestrator whose scope is wider than its own, as for `send`. A hand-off types into the agent it reaches, so this is `send` with a record: the governance review accepted it for agents in scope, since the edge leaves a visible, replayable trace.
- **As its auto hand-off would go.** Each auto edge is handed off along by the same code as a turn's end (`handOffAlong`): paused, it is skipped; its conditions are checked first and it is **held** while any fails; it delivers, or queues, as its rules say. A gate or script still runs only once the user approved it (ADR-0009): a hand-off never approves anything. A **manual** edge is left for the user to send, and reported so.
- **The edge's payload is the user's rule; the hand-off supplies its content.** A final-message edge takes `message` (named `message` in the hand-off line); a handover edge the file `handoverPath` (checked as an edge's path is: inside the worktree through any link, at most 64 KB), else its own file; a JSON edge the value `json` (at most 64 KB), else its own file. A final-message edge given no `message` is skipped, saying so: mid-turn, its last final message is from an earlier turn, and sending that would be wrong.
- **A copy is always kept of what was handed over.** What `message`, `handoverPath` or `json` gave is no file the daemon can read again at delivery, so a held or queued explicit hand-off keeps a copy whatever Settings › Held hand-offs says (ADR-0009). Switching that setting to path only drops the copies held then, as before; an explicit hand-off's dropped copy is then read again from the edge's own file. That is the one way it can deliver other than what was handed over, and only after the user chose to drop copies.
- **Its turn's end leaves those edges out.** The daemon keeps, per agent, the edges it handed off along this turn (delivered, held, queued or still checking; not skipped, nor one still checking that turns out skipped). Its `Stop` then hands off along its other auto edges only. The set belongs to one turn: the agent's own `UserPromptSubmit` starts a new one, and `StopFailure`, Codex's `Interrupt` and `SessionEnd`, which end a turn with no `Stop` after them, drop it too (`onTurnBoundary`). So a hand-off made in an interrupted or failed turn, or between turns, never stops a later turn's `Stop` from handing off. The set is kept in memory: a daemon restart between an explicit hand-off and its turn's `Stop` would hand off along that edge a second time, which we accept as rarer than the cost of storing it. So a hand-off isn't sent twice, and an agent without the Board MCP (an external session, a zone with the MCP off) works as before. The ticket read "flow edges fire on an explicit handoff when the agent has the Board MCP; Stop stays as the fallback": we didn't stop inferring for agents with the MCP, since every zone has it on by default and agents not told about `handoff` would never hand off at all.
- **It answers within seconds.** Each edge's outcome (`delivered`, `held`, `queued`, `skipped`, why) is returned; one whose conditions are still being checked after 5 s (`HANDOFF_ANSWER_MS`; a gate can take minutes, and Codex gives an MCP call 60 s) answers `checking`, and goes on; how it ends is logged when it does.
- **Handing off is finishing.** A `board.handoff` that doesn't throw sets the agent's `work_finished_at` (migration 0052), however each edge took it (delivered, held, queued, skipped), as `board.setStatus` with `done` does; the agent's own next `UserPromptSubmit` clears it. A turn ending is not finishing: an agent may end turns while a gate runs in its background. Its tile shows Finished, and its orchestrator hears it once (ADR-0011's crew events).
- **Logged.** Each edge handed off along is a line in the activity log (`orchestrator_activity`, action `handoff`), its target that edge's `to`, its detail what it carried and how it went; one that answered `checking` gets a second line once it is delivered, held, queued or skipped; a refused call is logged as refused. So an agent that hands off gets an Activity tab.
- **What it reaches.** A hand-off types into the `to` agent, as `deliver` always did at a turn's end: `handoffLine` strips control characters and heads it "Hand-off from A (its …):", so it never starts as a `/` or `!` command. Along its edges, it reaches the agents the board's edges already let A's turn's end reach; named, an agent in A's scope, over a one-off edge (above).

## Edges an orchestrator makes

- `orchestrator.addEdge { token, from, to, payload?, path?, trigger?, conditions?, deliverAs? }` and `orchestrator.removeEdge { token, id }` join `ORCHESTRATOR_METHODS`: the guard lets them through only while the token's agent may orchestrate, and each checks it again. A user-side session (a shell, or the user with no token, ADR-0011) calls them too, at board scope, and its edges are the user's own (`madeBy` null).
- **Scope.** Its `from` end must be an agent it may look at (`checkTarget`), its `to` end one it may steer (`checkSteerable`), or itself at either end. An edge into an agent is a way to type into it, so an orchestrator can't wire into one whose scope is wider than its own (`board` > `repo` > `zone`, the governance review's G29, as for `send`). An edge out of another orchestrator only carries what that one hands off, so it may.
- **Made as the user's are, but never approved or paused.** It goes through the same `create` as `flowEdge.create` (one edge per pair, no auto loops, the same checks of payload, path and conditions), with `paused` forced off and any `approvals` ignored: a gate or script on it holds until the user approves it in Edge rules. `flowEdge.create`, `update`, `send`, `approve`, `drop`, `delete` and `lastPayload` stay refused to every board token.
- **Marked.** `flow_edges.made_by` (migration 0038, no foreign key, so it still says an agent made it after that agent is deleted) is `FlowEdge.madeBy`. The board drew it dashed until every edge became a dashed rail (CD4); now its token's tooltip and its Edge rules say who made it, and the CLI says "made by". The user changes or deletes it like any other; an undo that makes it again makes it the user's.
- **Relaunching an ended `to`, as the user's do (G30).** A delivery along any edge an orchestrator wired relaunches an ended `to`, as the user's do (a named hand-off's one-off edge never does, above), and `addEdge` takes an ended `to`. Before the governance review an agent's edges skipped an ended `to` and only the user's Send started it again; the governance review found that only got in the way of a loop the user had already let the orchestrator wire, and `orchestrator.send` still refuses an ended agent.
- **Listing.** `edge list` (and the `list_edges` tool, for orchestrators) is `agent-board edges`; any agent can read every edge (`board`, `connections`).
- **Removing: its crew's (G32).** `removeEdge` takes an edge the orchestrator made, or one an agent in its crew made (its `spawnedBy` subtree), and refuses any other, the user's included. A user-side caller removes any edge, as the user does in the app.
- **Logged.** `add-edge` and `remove-edge` lines, done or refused, their target the edge's `to` agent.

## What an edge last delivered

The ticket asks for the payload to be viewable on click. The daemon keeps each edge's last delivered payload (name, text as delivered, JSON on one line, and when) **in memory only** (`flowEdge.lastPayload`, the user's alone): it can be anything the agent wrote, and ADR-0009 keeps such copies out of SQLite where it can. A daemon restart forgets it, and the panel says so. Under the edge's label a chip says when it last delivered ("delivered 14:02"); clicking it selects the edge, whose Edge rules show **Last hand-off**.

## Considered options

- **Stop inference off for agents with the Board MCP**: rejected (above).
- **Letting `handoff` fire manual edges**: rejected. Manual means the user presses Send.
- **Letting `handoff` name any agent**: rejected. It would be `send` for every agent, without the orchestrator's checks. The governance review lets it name an agent in its scope, with `send`'s check against wider orchestrators, over a one-off edge that records it.
- **Letting an orchestrator remove any edge in scope**: rejected, as for agents: what the user made stays the user's to delete. Only its own, the first rule, became its crew's after the governance review, so a lead can clean up after its workers.
- **Keeping the last payload in SQLite**: rejected for ADR-0009's reason.
